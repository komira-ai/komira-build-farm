The kbf worker daemon.

Usage: kbf-daemon [OPTIONS] --server <SERVERS> --ca-cert <CA_CERT> --cert <CERT> --key <KEY> --node-id <NODE_ID> --driver <DRIVERS>

Options:
      --server <SERVERS>
          A kbf-server worker listener to connect to, as an `https://host:port` URL; repeatable, or several separated by commas. The host may be a DNS name with a record per server: every round of attempts resolves it again and tries each address. The daemon never stops trying (see `--reconnect-max-ms`)

      --ca-cert <CA_CERT>
          PEM file of the CA certificates that sign server certificates

      --cert <CERT>
          PEM file of this daemon's client certificate chain

      --key <KEY>
          PEM file of this daemon's private key

      --tls-server-name <TLS_SERVER_NAME>
          The name to verify in the server certificate, when it is not the URL's host

      --node-id <NODE_ID>
          A stable name for this node, unique within the cell

      --reconnect-ms <RECONNECT_MS>
          The wait, in milliseconds, after a session ends and after the first round of connection attempts that all failed. It doubles with each further failed round
          
          [default: 1000]

      --reconnect-max-ms <RECONNECT_MAX_MS>
          The longest wait between rounds of connection attempts, in milliseconds. Each wait is jittered down by up to half
          
          [default: 30000]

      --label <KEY=VALUE>
          A node label, `key=value`, reported as `label.<key>`; repeatable. A Mac in komira's pool runs with `--label pool=darwin-sized`

      --storage-dial-timeout-ms <STORAGE_DIAL_TIMEOUT_MS>
          The longest, in milliseconds, that dialling a storage node may take: for its TCP connection and for its TLS handshake each. Must be 1 to 3600000 (one hour)
          
          [default: 10000]

      --storage-ping-interval-ms <STORAGE_PING_INTERVAL_MS>
          How often, in milliseconds, a connection to a storage node with a call on it is pinged (HTTP/2 PING). Must be 1 to 3600000 (one hour)
          
          [default: 10000]

      --storage-ping-timeout-ms <STORAGE_PING_TIMEOUT_MS>
          How long, in milliseconds, a ping to a storage node may go unanswered before the connection is dropped and the calls on it fail over to the next owner. Must be 1 to 3600000 (one hour) and no more than `--storage-ping-interval-ms`
          
          [default: 10000]

      --driver <DRIVERS>
          How leases run; once per runtime. The daemon runs each lease on the driver that serves its kind and refuses to start when two serve the same kind. The node's own driver (native or container) is set up first, whatever the order given

          Possible values:
          - fake:                 Runs nothing; every action succeeds with an empty result. For bring-up only
          - container:            Each action in a fresh rootless Podman container (Linux)
          - native:               Each action as plain processes on the node, for Macs
          - native-whole-machine: Each whole-machine lease as its own user in its GUI session, through `kbf-mac-session` (macOS)

      --cas <CAS>
          The server's worker listener, an `https://` URL (normally `--server`'s), that the container and native drivers read and write blobs through, over mutual TLS with this daemon's `--ca-cert`, `--cert`, `--key` and `--tls-server-name`. Plain `http://` is refused: the worker listener admits each blob call by the daemon's certificate. Every driver's blobs go through one transfer engine, over one connection, within the `--transfer-*` limits

      --data-dir <DIR>
          The directory the daemon keeps everything in, on a local disk: `leases/` (lease directories, the container and native drivers), and under the container driver (and the native driver on macOS) `cache/` (the input cache, `docs/design/worker-cache.md`) and `trees/` (shared read-only input trees, `docs/design/fast-sandbox.md#4-shared-trees`). Made if missing; absolute. The cache and trees are on, sized from the filesystem: half and a quarter of its size less what it keeps free (5%, at least 1 GiB), and the cache evicts entries no running lease links to keep that much free. A directory another daemon owns, or that cannot be used, is left alone: the daemon warns and runs uncached.
          
          Default `/var/lib/kbf`. A daemon with the fake driver alone touches no directory unless this is given.

      --data-max-bytes <BYTES>
          Lowers the size the cache and the trees are budgeted from (half and a quarter of it), under the filesystem's automatic one

      --output-max-depth <MAX_DEPTH>
          The deepest directory an output directory may hold, in levels below it (its own entries are level 1)
          
          [default: 512]

      --output-max-entries <MAX_ENTRIES>
          The most entries (files, directories, symlinks and anything else) one action's outputs may hold together, the declared outputs included
          
          [default: 1000000]

      --output-max-bytes <MAX_BYTES>
          The most bytes one action's output files may hold together
          
          [default: 17179869184]

      --output-max-stdio-bytes <MAX_STDIO_BYTES>
          The most bytes each of the action's stdout and stderr may hold
          
          [default: 1073741824]

      --reserve-cpus <N>
          Logical CPUs the farm's own processes keep, in CPUs (hyperthreads count one each). The daemon gives its leases every CPU it may use but these, with no pinning, and sizes its own pools from them. Default: 8 (half the CPUs on a machine of fewer than 16). 0 is allowed; a value that leaves no CPU for leases, or is more than the machine has, is refused. On a host that also runs the server, this covers both; the server has no reserve flag

      --reserve-share <N>
          How many of the farm's processes on this host share the reserve: the daemon sizes its pools from `reserve / share` CPUs. Default 1

      --async-threads <N>
          Worker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use on the server; `max(2, reserve/4)`, at most the physical cores, on the daemon

      --blocking-threads <N>
          The most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's) for the server, 64 for the daemon

      --cpu-threads <N>
          Threads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use on the server; `max(2, reserve/2)`, at most the physical cores, on the daemon

      --output-upload-deadline-secs <OUTPUT_UPLOAD_DEADLINE_SECS>
          How long one lease's whole output upload (its output files, stdout and stderr) may take, in seconds, before the lease fails with a reason naming the upload and the time it ran (container and native drivers). Without it, a store that stops answering holds the lease, and its slot, with no error
          
          [default: 1800]

      --transfer-in-flight <TRANSFER_IN_FLIGHT>
          The most blob requests in flight at once, for the whole daemon: ByteStream reads and writes, segment ranges and FindMissing calls, over its one connection to `--cas`. Uploads hold at most all but a quarter of them
          
          [default: 64]

      --transfer-bytes-in-flight <BYTES>
          The most bytes of blobs read into memory in flight at once, for the whole daemon. A blob larger than this is fetched alone
          
          [default: 268435456]

      --transfer-memory-blob-bytes <BYTES>
          The largest input file fetched through memory, where every lease asking for it at once shares one fetch; a larger one is streamed into its file
          
          [default: 1048576]

      --transfer-chunk-bytes <BYTES>
          The most bytes one ByteStream write message carries
          
          [default: 1048576]

      --transfer-find-missing-chunk <TRANSFER_FIND_MISSING_CHUNK>
          The most digests one FindMissing call asks about
          
          [default: 1000]

      --transfer-stream-window-bytes <BYTES>
          The HTTP/2 window of each stream to `--cas`; the connection's is eight times it
          
          [default: 8388608]

      --transfer-retries <TRANSFER_RETRIES>
          How many times a blob request is retried after UNAVAILABLE or a broken connection
          
          [default: 3]

      --segment-upload-streams <SEGMENT_UPLOAD_STREAMS>
          How many `PutRange` calls one segment upload of an action's outputs has in flight at once, as HTTP/2 streams on the one connection to `--cas` (`docs/design/write-path.md`, section 4.1); also the parallel `ReadRange` calls of a segment-range read
          
          [default: 16]

      --segment-uploads-in-flight <SEGMENT_UPLOADS_IN_FLIGHT>
          How many segment uploads of one action's outputs are in flight at once: the server checks and stages one upload while the next are sending (`docs/design/write-path.md`, section 4.1). Their `PutRange` calls still take permits of `--transfer-in-flight`'s uploads' share
          
          [default: 4]

      --cgroup-parent <CGROUP_PARENT>
          The cgroup lease cgroups are made under, from the cgroup root (container). Left out, the daemon sets up its own cgroup, which its systemd unit must delegate (`Delegate=yes`): it moves itself into a `supervisor` leaf there and makes `actions` beside it, with cpu, memory and pids enabled. Given, it must already enable cpu, memory and pids for its children

      --actions-memory-max-gib <ACTIONS_MEMORY_MAX_GIB>
          Written to the actions cgroup's `memory.max` at start (container): the most memory all leases together may use, in GiB, so the rest stays for what else runs on the node. The node reports the lowest `memory.max` above its leases, or its memory when that is less, and the CPUs of their cpuset

      --supervisor-memory-min-mib <SUPERVISOR_MEMORY_MIN_MIB>
          Written to the daemon's `supervisor` leaf's `memory.min` at start, in MiB (container, without `--cgroup-parent`): memory the kernel does not reclaim from the daemon while it uses no more, so builds short of memory never take it. The kernel protects no more than the unit's and its slice's `MemoryMin=` allow; the daemon warns when one is lower. 0 protects nothing
          
          [default: 256]

      --container-pids-limit <CONTAINER_PIDS_LIMIT>
          Each container's `pids.max`: its tasks, threads included (container)
          
          [default: 8192]

      --container-shm-mib <CONTAINER_SHM_MIB>
          The size of each container's `/dev/shm`, in MiB (container)
          
          [default: 64]

      --container-nofile <CONTAINER_NOFILE>
          Each container's open-file limit, soft and hard (container). Rootless, it cannot exceed the daemon's own hard limit
          
          [default: 65536]

      --container-nproc <CONTAINER_NPROC>
          The process limit, soft and hard, of each container's user (container). Every container's root is the same host id, so it bounds all the node's actions together
          
          [default: 32768]

      --lease-swap-kill-mib <LEASE_SWAP_KILL_MIB>
          A lease at its own memory cap is killed, and reported out of memory, once it has pushed more than this many MiB into swap at its cap... (container)
          
          [default: 512]

      --lease-swap-kill-percent <LEASE_SWAP_KILL_PERCENT>
          ...or this percentage of its booked memory, whichever is more. The kernel caps each lease's RAM at its booking x 1.5 + 512 MiB and lets it swap without limit; a lease is killed by this rule only while its own cap keeps being hit (its `memory.events` `max` grew since the last sample) and its swap rose since the last sample, and only swap that rose so counts, never swap that host pressure moved out of it
          
          [default: 25]

      --memory-pressure-pause-percent <MEMORY_PRESSURE_PAUSE_PERCENT>
          The daemon takes no new lease while the node's memory stall time (the `some` line's `avg10` in `/proc/pressure/memory`, as a percentage) is above this and it runs a lease: it says so to the server, which places nothing on it until the stall falls, and the leases it runs go on. With no lease it serves whatever the stall, so it is never left idle for good. Off where the kernel reports no pressure stall information (macOS, a kernel built without it)
          
          [default: 10]

      --lease-swap-poll-ms <LEASE_SWAP_POLL_MS>
          How often each lease's `max` events and swap are sampled, in milliseconds (container)
          
          [default: 1000]

      --memory-limit-percent <MEMORY_LIMIT_PERCENT>
          A lease's processes are killed past this percentage of its booked memory...
          
          [default: 150]

      --memory-headroom-mib <MEMORY_HEADROOM_MIB>
          ...plus this many MiB (native). A lease that booked nothing has no limit
          
          [default: 512]

      --memory-poll-ms <MEMORY_POLL_MS>
          How often a lease's memory is measured, in milliseconds (native)
          
          [default: 250]

      --xcode-apps <XCODE_APPS>
          The directory searched for `Xcode*.app` (native). Each Xcode whose own `xcodebuild` answers `-version`, `-license check` and `-checkFirstLaunchStatus`, and for which `xcrun --find clang` does (each within a minute, under the actions' sandbox), is ready: it is reported as an `xcode` entry, and an action that names its build runs with it as `DEVELOPER_DIR`. One that is not is listed in the node's status with why and the command that fixes it, and logged at WARN. The daemon says Hello without waiting for its first survey, which runs in the background: until it ends, each Xcode is listed as not surveyed yet and none is reported
          
          [default: /Applications]

      --xcode-recheck-secs <XCODE_RECHECK_SECS>
          How often, in seconds, the Xcodes are asked again (native), so one fixed while the daemon runs becomes ready without a restart
          
          [default: 180]

      --require-metal-toolchain
          This node's actions use Metal (native): an Xcode whose Metal toolchain is not installed (`xcodebuild -showComponent MetalToolchain`) is not ready

      --image <IMAGE>
          A container image this node is pinned to, as an action names it: `docker://<repo>@sha256:<digest>`, one architecture's manifest digest (container; repeatable). At start the daemon checks each is in its user's image store, as the prepare step of every lease does, and exits with status 2 if one is not, or names an image index, saying the fix (`podman pull <repo>@sha256:<d>`). The node's status lists them (`GET /v1/nodes`, `software.container_images`). No work is placed by image yet: an action may still name another image

      --container-runtime <podman|oci>
          The runtime that runs each action's container (container): `podman`, the default, runs `podman create` and `podman start` per action; `oci` runs each action in a fresh rootless sandbox through `--oci-runtime` directly, with no Podman on the action path (Podman only pulls and exports an image once per digest). `oci` needs the daemon user's subordinate ids in one range, `uidmap`, and every directory down to `--data-dir` searchable by others
          
          [default: podman]
          [possible values: podman, oci]

      --lease-placement <none|numa-node>
          Where each lease runs among the node's CPUs (container, Linux): `none`, the default, lets a lease use any CPU the daemon may; `numa-node` puts each lease on one NUMA node, its CPUs (`cpuset.cpus`) and memory (`cpuset.mems`), the node with the least CPU booked by running leases (the lowest id on a tie). `--reserve-cpus` is a quota on all leases together, so it still applies; it removes no CPU from a node. Needs the `cpuset` controller delegated to the daemon (the start fails and says how when it is not); a host with fewer than two NUMA nodes that hold CPUs runs as `none`, which the start logs. Refused with a driver other than `container` (macOS has no such driver)
          
          [default: none]
          [possible values: none, numa-node]

      --oci-runtime <OCI_RUNTIME>
          The OCI runtime `--container-runtime=oci` runs actions with (container)
          
          [default: /usr/bin/crun]

      --mac-session-socket <MAC_SESSION_SOCKET>
          The socket `kbf-mac-session` serves (native-whole-machine)
          
          [default: /var/run/kbf-mac-session/socket]

      --daemon-user <DAEMON_USER>
          This daemon's own user, which keeps read and remove access to what a whole-machine lease's user writes in its lease directory (native-whole-machine)
          
          [default: _kbf]

      --pool-users <POOL_USERS>
          How many lease users the pool has (native, macOS, a daemon run as root): every action runs as one of `kbf-pool-0` .. `kbf-pool-<N-1>`, one lease per user at a time, as kbf-mac-provision makes them (`pool_users`). Required of a root daemon, which runs no action as root; refused for any other

      --pool-first-uid <POOL_FIRST_UID>
          The uid of `kbf-pool-0`, and the group id of all the pool users (`pool_first_uid` in kbf-mac-provision's profile); at least 600

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version
