The kbf farm server

Usage: kbf-server [OPTIONS]

Options:
      --role <ROLE>
          The roles to run

          Possible values:
          - all: Front, scheduler and metadata in one process
          
          [default: all]

      --cold-store <URI>
          The durable object store, where every blob ends up: `file:///absolute/path` (a directory, `kbf_objstore::FsStore`: locked while the server runs, a second server on it is refused; a write that would leave its filesystem with less free than it keeps, 5% of its size and at least 1 GiB, is refused and wakes the evictor, which forgets the least recently used objects (never one used in the last minute) and deletes their files while less than twice that is free) or `s3://bucket/prefix?endpoint=http://host:port` (MinIO, RustFS; the key pair is `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`; query keys `region`, `conditional-put=true` for a store that refuses to overwrite a key, and `min-put-rate=BYTES_PER_SEC`, the slowest rate a PUT body may reach the store at: a PUT is cut after 60 seconds plus its body's length at that rate, 1 MiB/s by default). Objects are keyed under `<prefix><log id>/` (`kbf/` for a directory and for an S3 URI without a path), the id of the metadata log. A directory is checked against the index by a start-up pass in the background; a lost or damaged object is also found when it is read, or before an action-cache hit that needs it is served (a miss). There is no `memory:` store: a `file://` path on a tmpfs is one

      --hot-store <URI>
          The fast tier in front of the cold store: `file:///absolute/path`, a directory on an SSD (or a tmpfs). Uploads land there and are flushed to the cold store in the background; reads are served from it while a blob is still there. Its budget is not a flag: 80% of the filesystem's free space less what it keeps free (5% of its size, at least 1 GiB, and never more than half of what is free), at most `--hot-store-max-bytes`; at the budget, writes take the direct path to the cold store. Without it, uploads go straight to the cold store. A daemon's outputs (a segment upload, or the in-process plane) and a ByteStream Write over 16 MiB are written through to it as they arrive, so a large one is never held in memory. Without it, or when it has no room, a daemon's blob over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) is streamed to the cold store as it arrives (a ByteStream Write, or the in-process plane's own stream), never held whole and never refused for its size. The first start with a hot store raises the metadata log to machine version 2, once; a binary that runs only version 1 no longer reads it. The metadata log lives in `<dir>/meta`, unless `--meta-dir` says otherwise

      --hot-store-max-bytes <BYTES>
          The most bytes the hot store's block files may hold before they are flushed, lower than its automatic budget

      --hot-store-abandon <ID>
          Abandons this server's hot store tier `<id>` at start: every object staged on it is marked unreachable as missing (its blobs answer `Unavailable` until uploaded again; nothing is answered `NOT_FOUND`), and the directory becomes a new tier. For a lost or replaced disk, after a start was refused because the directory's `TIER` file is missing or names another tier. The id is the one the refusal names

      --meta-dir <DIR>
          The directory of the metadata log (the CAS index and the action cache, a single-voter Raft log), on a local disk; created if missing. An empty directory gets a new log with a new id; every later start over it reads the id from the directory. Left out, it is `<hot store directory>/meta`; required when there is no `file://` hot store. Given, it wins over the hot store's directory

      --state-store <URI>
          Where the scheduler keeps its state, written before each change is acknowledged and replayed at start: `sqlite:///absolute/path` (a file on a local disk that this process owns; every start is a new epoch, so daemons kill the runs of the leases they held before) or `postgres://...` (a database that outlives the process; a start keeps its epoch, so daemons keep their runs). Any other scheme is refused. This build has neither backend yet: a start with the flag is refused. Left out, the scheduler's state is in memory and a restart loses it

      --log-dir <DIR>
          The directory of the durable log file, `kbf-server.log` and its rotated `kbf-server.log.1`, `.2`, ... (created if missing): every event stderr gets, in the same format, kept across restarts. Left out, it is `<hot store directory>/log` when the hot store is a directory; with neither, there is no file and the server logs to stderr alone (the start logs which). A directory or file that cannot be written never stops the server ([`crate::log_file`])

      --log-max-bytes <BYTES>
          The most bytes one log file holds before it is rotated; a line longer than this goes alone to a fresh file. With `--log-files` it bounds the log's size on disk
          
          [default: 67108864]

      --log-files <N>
          How many log files are kept, the current one included; rotation drops the oldest. The log never exceeds `--log-max-bytes` times this, plus one line
          
          [default: 8]

      --listen <LISTEN>
          The REAPI listener. Without `--reapi-tls-cert` and `--reapi-tls-key` it serves plain text, on any address; off loopback the start line carries a warning
          
          [default: 127.0.0.1:8980]

      --reapi-tls-cert <REAPI_TLS_CERT>
          PEM certificate (chain) of the REAPI listener. With `--reapi-tls-key` it serves TLS with this server certificate only; clients present no certificate. It is meant for a certificate from the farm's own internal CA, trusted by the front's proxy (its hop to this server) and by clients that dial this server directly; TLS for the farm's client-facing name still ends at the front. `--reapi-auth-policy` applies over TLS as over plain text

      --reapi-tls-key <REAPI_TLS_KEY>
          PEM private key of the REAPI listener; it must match `--reapi-tls-cert`, or the server refuses to start

      --reapi-auth-policy <REAPI_AUTH_POLICY>
          A JSON file with the REAPI listener's authentication policy and authorizers (`docs/reapi-auth.md`), read once at start; a file that is not a valid policy stops the server. Without it every REAPI call is accepted and allowed. The worker listener does not read it; on the operator API only the build pages and the blob route do, and they are off unless it names their authorizers

      --worker-listen <WORKER_LISTEN>
          The `kbf.worker.v1` listener. Without mutual TLS (`--worker-tls-cert`, `--worker-tls-key`, `--worker-client-ca`) it serves plain text, on any address; off loopback the start line carries a warning
          
          [default: 127.0.0.1:8981]

      --api-listen <API_LISTEN>
          The operator API listener (HTTP/JSON under `/v1`). Off unless given. Reads are open to whoever reaches it: bind it where only operators do

      --api-token-file <API_TOKEN_FILE>
          A file holding the token operator API writes (cordon, drain, uncordon) must present as `Authorization: Bearer <token>`. It must be owned by the server's user with mode 0600 or 0400, or the server refuses to start; run the server as a user other than the daemon's, whose builds could read it. Without it, writes are refused

      --invocations-open
          Serves the build pages (`GET /v1/invocations/{id}` and below) and the blob route (`GET /v1/blobs/{digest}`) on the operator API to every caller the REAPI policy accepts, with no `invocations` or `blobs` key in the policy file (`docs/design/invocations.md` section 4.3): it fills in `allow` for whichever of the two keys the file leaves out. Without it, and without the keys, those routes answer 404. Pages and blobs hold build outputs and logs: give it only for a listener that only trusted people reach

      --readyz-store-timeout-ms <READYZ_STORE_TIMEOUT_MS>
          How long, in milliseconds, `GET /readyz` on the operator API and the REAPI listener's `grpc.health.v1` service wait for the object store to answer their read-only probe before they answer not ready
          
          [default: 2000]

      --worker-tls-cert <WORKER_TLS_CERT>
          PEM certificate of the worker listener. With `--worker-tls-key` and `--worker-client-ca` it serves mutual TLS; without all three, plain text

      --worker-tls-key <WORKER_TLS_KEY>
          PEM private key of the worker listener

      --worker-client-ca <WORKER_CLIENT_CA>
          PEM CA that daemon client certificates must chain to

      --worker-deny-list <WORKER_DENY_LIST>
          The worker listener's deny list: certificate serials, public keys and node ids it refuses (format in the `identity` module docs). Read at start, then again at every `Hello` and `Heartbeat`, so an edit takes effect without a restart. Needs mutual TLS

      --heartbeat-interval-ms <HEARTBEAT_INTERVAL_MS>
          The heartbeat interval daemons are asked for, in milliseconds, at most half the window in which a daemon may act on a `Start` (each `Start` names the newest heartbeat the server took, so a longer interval would leave it too little)
          
          [default: 5000]

      --unservable-wait-secs <UNSERVABLE_WAIT_SECS>
          How long, in seconds, queued work waits while no connected daemon can run it (none satisfies its platform, or none that does is large enough) before it is refused FAILED_PRECONDITION. The wait restarts whenever one can
          
          [default: 300]

      --memory-ladder-gib <MEMORY_LADDER_GIB>
          The memory rungs of an action, in GiB, ascending and each at least 1. The first is what an action that names no size (`kbf-book-mem-gib`) books. An action that passes its own memory limit runs again on the next rung above what it booked, and after the last on a whole host: the memory of the largest node that could run it, so that no other lease fits there. A rung not below that node's memory is skipped for the whole host. An action that does finish keeps its rung: later runs of it start there
          
          [default: 4 16 32]

      --finished-retention-secs <FINISHED_RETENTION_SECS>
          How long, in seconds, a finished operation is kept after its callers are answered. Within it, WaitExecution on the operation's name streams its result (a client whose Execute stream broke gets a result the action cache does not keep, such as a failure); after it, the name is NOT_FOUND. Every operation finished within it is held in memory
          
          [default: 60]

      --shutdown-timeout-secs <SHUTDOWN_TIMEOUT_SECS>
          How long, in seconds, a stop (SIGINT or SIGTERM) waits for REAPI clients to finish: it refuses new Execute calls (UNAVAILABLE, which Buck2 retries) and sends GOAWAY, and every open Execute and WaitExecution stream stays open until its action is done. Buck2 never recovers a stream that breaks mid-action, so the default, 0, is no deadline; set one at least as long as the longest action. When it runs out, the open streams end UNAVAILABLE (a client still uploading is cut off)
          
          [default: 0]

      --progress-interval-secs <PROGRESS_INTERVAL_SECS>
          How often, in seconds, every open Execute and WaitExecution stream is sent its operation again (same name, not done, current stage), so a load balancer's idle timeout never cuts a long action. 0 sends none
          
          [default: 30]

      --http2-keepalive-interval-secs <HTTP2_KEEPALIVE_INTERVAL_SECS>
          How often, in seconds, the REAPI and worker listeners send an HTTP/2 PING on a quiet connection. 0 sends none (and `--http2-keepalive-timeout-secs` is unused)
          
          [default: 30]

      --http2-keepalive-timeout-secs <HTTP2_KEEPALIVE_TIMEOUT_SECS>
          How long, in seconds, a PING may go unanswered before the connection is closed
          
          [default: 20]

      --async-threads <N>
          Worker threads of the async runtime, which run every task between its waits. Default: every CPU the process may use on the server; `max(2, reserve/4)`, at most the physical cores, on the daemon

      --blocking-threads <N>
          The most threads the runtime's blocking pool runs at once, for calls that wait on a disk or a process (a thread is made when a call needs one and ends when idle). Default: 512 (tokio's) for the server, 64 for the daemon

      --cpu-threads <N>
          Threads for CPU-bound work, such as hashing, which never waits and so is held to the CPUs. Default: every CPU the process may use on the server; `max(2, reserve/2)`, at most the physical cores, on the daemon

      --invocation-memory <INVOCATION_MEMORY>
          The memory, in bytes, the invocation records may take together (`docs/design/invocations.md`, section 3.5). At the bound, records of a minted id go first, then idle ones, least recently seen first; with only open builds left, the largest stops taking rows. Records are kept in memory only and lost on restart. Their heap was measured at up to 1.08 times this at 200 kB and above, and 1.12 at 50 kB (section 3.5)
          
          [default: 268435456]

      --segment-upload-max-bytes <BYTES>
          The most bytes, records and footers together, one segment upload on the worker listener may hold in memory (`docs/design/write-path.md`, section 4.2): the segments it declares that are not written to the hot store as they arrive (all of them, without one). Not a limit on a blob's size: a segment held in memory holds no record over 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`), and an upload with a larger one and no room on the hot store is answered FAILED_PRECONDITION, so the daemon sends its records by ByteStream, which streams a large blob to the cold store. Those ranges are held until the upload commits, admitted under `--write-bytes-in-flight` with every other upload: a `Begin` waits while that is spent. At least 33 MiB (`kbf_front::MIN_SEGMENT_UPLOAD_BYTES`), a daemon's upload of small files with room to spare, and at most `--write-bytes-in-flight`, so any legal `Begin` can be admitted; the server refuses to start otherwise. At most `kbf_front::MAX_ADMISSION_BYTES`, the most one admission counts, so a `Begin` never holds more than it is counted for under the bound
          
          [default: 34603008]

      --segment-upload-idle-secs <SEGMENT_UPLOAD_IDLE_SECS>
          How long, in seconds, a segment upload may go without a call before it is dropped and its memory returned. An upload is also dropped when the connection that began it closes; one that is committing is kept until its commit ends
          
          [default: 60]

      --write-linger <WRITE_LINGER>
          How long, in milliseconds, the oldest blob of an open segment waits for concurrent uploads to join it before the segment is sealed and written (`docs/design/write-path.md`, section 3.1). No caller is answered before its segment has committed, so this is added to an upload's latency at most
          
          [default: 2]

      --write-own-segment-bytes <WRITE_OWN_SEGMENT_BYTES>
          Blobs of this many bytes or more are written as a segment of their own, past the group, so they neither wait for the linger nor hold up small writes
          
          [default: 16777216]

      --write-bytes-in-flight <WRITE_BYTES_IN_FLIGHT>
          The most bytes uploads may hold at once. A ByteStream Write is admitted before it reads past its first message, for its blob's size up to 16 MiB (`kbf_front::MAX_UNSTAGED_BLOB_BYTES`) and for 16 MiB above that (a larger blob is streamed onto the hot store, or to the cold store without room there, not held); a BatchUpdateBlobs for its total; a segment upload's Begin for what it holds in memory. A caller over the bound waits, nothing is refused for load. At least `--segment-upload-max-bytes` (by default 33 MiB, under the default 2 GiB). Not covered: each HTTP/2 stream's message as tonic decodes it, before the handler runs, up to 17 MiB per stream (about 3.4 GiB for 200 streams), times the streams one connection may open (each listener's `-max-streams` flag)
          
          [default: 2147483648]

      --reapi-max-streams <REAPI_MAX_STREAMS>
          The most HTTP/2 streams one connection to the REAPI listener may have open. buck2 keeps one Execute stream open per outstanding action, idle until the action finishes, so this bounds how large a backlog one buck2 invocation can show the farm. The connection's flow-control window is this many streams' windows; above about 2000 streams each stream's window is smaller than 1 MiB so that the product stays under HTTP/2's largest window. At least 1, at most 32767
          
          [default: 10000]

      --worker-max-streams <WORKER_MAX_STREAMS>
          The most HTTP/2 streams one connection to the worker listener may have open: a daemon's persistent session stream and its short transfer streams. At least 1, at most 32767
          
          [default: 200]

      --write-puts-in-flight <WRITE_PUTS_IN_FLIGHT>
          The most segment PUTs, each with its footer read-back, in flight at once. A segment sealed while all are busy waits; new blobs go to a new open segment
          
          [default: 4]

      --store-put-attempts <STORE_PUT_ATTEMPTS>
          How many times a segment PUT is tried. Only a PUT that did not complete (connect, reset, timeout) or that the store answered 5xx is tried again, after 100 ms and then four times longer each time, under a new object key; if every attempt fails, the segment's blobs are answered UNAVAILABLE
          
          [default: 3]

      --input-tree-cache-entries <INPUT_TREE_CACHE_ENTRIES>
          The most decoded Directories an Execute's input check keeps in memory (`docs/design/storage.md#input-tree-check`). Least recently used go first
          
          [default: 1048576]

      --input-tree-cache-bytes <INPUT_TREE_CACHE_BYTES>
          The most bytes of decoded Directories the input check keeps (each costs its digests, 40 bytes apiece, and 160 bytes)
          
          [default: 268435456]

      --input-tree-reads-in-flight <INPUT_TREE_READS_IN_FLIGHT>
          The most Directory blobs the input check reads from the store at once, across all Executes
          
          [default: 64]

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version
