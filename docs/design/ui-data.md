# kbf UI data: what the UI and its read API present

Status: design, nothing built beyond what is marked [F]. Data before visuals: this document says what the UI and its machine-readable read API must present, where each item comes from, how long it is kept and what it costs. It says nothing about layout. Labels as in `architecture-v2.md`: **[F]** fact checked in the code at this branch's merge-base with `feature/arch-v2`, `364da4ae` (this branch's commits above it touch only this document, `invocations-api.md` (4.7 and the passages that named PRs 7 and 8 or stage 2), supersession notes in `invocations.md` and the frontend and state-store text of `architecture-v2.md`, so code cites are the same at this branch's head), **[D]** owner decision, **[I]** inference, **[V]** verify before building on it. Sizes are arithmetic from stated rates, not measurements.

It builds on `invocations.md` and `invocations-api.md` (the per-build record and its read API) and on `architecture-v2.md` (frontend serves REAPI, scheduler and UI; a state store behind the `kbf-state` trait, SQLite and Postgres first; sharded storage). It does not redo them; it lists what the UI adds.

## Summary

The UI is a set of read-only pages over one JSON read API; an agent calls the same API and sees everything a page shows. What it answers, and what is missing today:

| User question | What answers it | Today / needs |
|---|---|---|
| Did my build pass; which actions failed and why; full logs; the exact command (D1 to D4) | invocation summary, `/actions`, `/failures`, decoded command, log tails | summary and `/actions` built, in memory only, lost on restart; `/failures`, which carries the decoded command, needs U1; logs last only as long as storage keeps the blob, so they need failure pins (U3) |
| Where did the time go; which actions were slowest; why did it wait (D5, D11) | all nine REAPI timestamps, phase totals, `sort=`, `top_slowest`, `wait_reason` | four times per attempt are kept; the rest needs U1 |
| Why did it OOM, what limit, what next time (D6) | memory fields on every memory-killed attempt, memory floor per digest | only a requeue keeps booked/raised; the final kill keeps none: U1, U2 |
| Is this test flaky, since when; first failing commit; is this action slower (D8, D9) | outcome records and daily rollups per shape and branch | nothing today: history (U3), commits from a client report (U4) |
| What is on the critical path (D10) | client report; else slowest actions and phase totals | client report (U4) |
| Nodes, queue, leases (O1 to O3) | `/v1/nodes`, `/v1/nodes/{id}`, `/v1/queue`, `/v1/leases` | `/v1/nodes` built (open, operator listener only); the rest needs U2 |
| Which node fails what passes elsewhere (O5) | per-node failure counts, runs by node and time | history (U3) |
| Storage health (O4) | storage map, repair and loss counts | arrives with the v2 storage phases P3 to P6 |
| Farm health now and over weeks (W1, W2) | `/v1/health`, built-in series | `/metrics` exists but resets at start: U5 |
| Remove a leaked secret (O6) | purge as a tombstone | U5 on one store, U8 across replicas |
| What idle capacity does (W3) | idle-host test reruns | U7, after preemption is built |

The biggest things to add:

- **Durable history as objects in the object store** (S3, MinIO or `file://`, the cold store's pluggable backends), written after commit and never on the acknowledgement path: run and hit records, log tails, outputs listings, node samples, test outcomes, rollups, series and client reports, batched into immutable chunk objects. The tables are only a **metadata store**: small index rows (invocation headers, chunk pointers, the shape catalog and per-shape status, pins) in the `kbf-state` backend, rebuildable from the objects. It replaces the Raft-based stage 2 of `invocations.md` and keeps its chunks (5.2).
- **Per-action fields kept in the row**: shape and `cfg`, the nine REAPI timestamps, the full cgroup block, memory-kill fields, wait reason, farm reruns, a timed-out run's logs. Today most exist only in log lines, blobs or scheduler memory, not in the row.
- **A client report** (one upload route, owner only, off without per-caller authentication) for what REAPI cannot carry: commit and branch, target names, critical path, test cases.
- **Pins for failure logs**: a failed run's logs and result kept 30 days within a byte budget shared per instance (Q21 asks whether copies into the object store replace them). Client reports are history objects kept 7 days under a per-owner quota. Nothing in storage can pin a blob today.

**Size.** At the assumed rate (about 4 operations a second, 9 cache hits per execution; assumptions, not measurements): about 18 GB of history objects (about 21.5 GB with the failure-log copies of Q21), about 14,000 PUTs (17,600 with Q21) and 46,000 GETs a day, about $3.1 a month at S3 list prices (about $3.7 with Q21; GETs dominate if the local cache misses, 5.3); a metadata store of at most about 0.5 GB written at about 1.5 rows a second through the day, at most about 80 a second at the burst and a rate-limited fold at day close, in background transactions that join a batch with a `Start` or `Result` only after waiting 250 ms or 16 batches, one at a time and behind them, and are guaranteed to progress (5.2); frontend disk is a cache only (default 4 GiB); plus the 20 GiB failure-pin budget in storage (5.3, 5.5). An earlier draft kept everything in tables: about 36 GB written at up to 6.6 MB/s of WAL.

**Phases.** U1 (per-action data) and U2 (farm-state reads) need no state store and ship on today's single frontend. U3 (history objects, metadata store and pins), U4 (client report), U5 (series, health, purge on one store, raw Command gate) and U6 (UI pages) need `kbf-state` on SQLite (P1) and an object store (`file://` on `all-in-one`), and still run on the single frontend; U7 (idle-host tests) also waits for preemption; U8 (purge across replicas) waits for P5 and P6 (section 9).

**Decisions.** **[D]** The owner accepted every recommendation of section 10 (Q1 to Q19), with two changes: the state store is an interface that any backend may implement by passing the conformance suite, SQLite and Postgres first (`architecture-v2.md` 4.1); and bulk history lives in the object store, with the tables reduced to a metadata store of index rows (section 5). Q1, Q2, Q5, Q6 and Q19 are recorded as amended by that. Q20 and Q21, raised by the redesign, are open.

## 1. Decisions

All **[D]** by the owner (section 10).

- **One surface.** The UI reads only the JSON read API of section 6. Every page names the API calls it made. An agent therefore gets everything the UI shows, machine-readable, with the same authority.
- **History in the object store, a small index in the metadata store.** Per-run records, hits, tails, outcomes, rollups, series and reports are immutable objects in the object store (section 5), written after the state-store commit, never on the acknowledgement path. Tables hold only index rows that point into those objects, under a `ui/` namespace of the `kbf-state` trait, so every state-store backend serves them and a frontend that is stateless on Postgres stays stateless; its local disk is a cache (5.5). It also becomes the durable home of invocation records, replacing the Raft-based stage 2 of `invocations.md` 3.5 (that log is removed by v2).
- **Every history record and index row carries its instance name**, and every read is filtered by the caller's authority on that instance, as the built invocation routes are (section 8).
- **Shape identity covers every action** (kbf#765), refined by `cfg` and by a target name when one is known. Tests are the shapes marked as tests; the farm never needs the client to say "this is a test".
- **Built fields keep their names and formats.** New data adds keys; nothing built is renamed (6.1).
- **[D] The farm never keys its data on what a client says (owner, 2026-10-16).** A client bug must not be able to misattribute farm data. Metrics are measured by the farm; the target label is derived on the server from each action's own output paths (`<cell>/<pkg>/__<name>__/`, read by the shape parser; komira-ai/komira-build-farm#796), `target: null` where paths are hashed; a client `target_id` is shown only as a hint. Commit and branch become keys (first failing commit, history per branch, 4.3) only when the farm itself fetched that commit (the async remote build job, a later phase); a commit in a client report is shown as `reported_commit` and is never a key.
- **The client may add what REAPI cannot carry** (critical path, test cases, a reported commit) through one upload route, written only by the record's owner, and only on a farm whose policy authenticates each caller (4.6, 8). It is display-only enrichment beside the farm's data, never a key. Nothing in the farm requires it.

### 2.2 What agents worked out by hand

**[I]** From agents debugging builds on this farm (generic shapes only): they could not tell a farm fault from an action failure without the server log (D2); they read the daemon journal on a node to find why the farm could not run an action, because the reason reaches only a server WARN line (`crates/kbf-server/src/farm.rs:610-618`); they found that the client's reported duration includes farm queue time and took phase times from the daemon's `lease phases:` line instead (D5); a container's OOM flag was false for an exit-137 kill, so they counted kernel memcg kills (D6); memory-ladder rungs looked like failures; they reran single tests by hand to judge flakiness (D8); they could not reach `/metrics` and `GET /v1/nodes` (O1). **[F]** Those two routes need no token: they are open reads (`crates/kbf-server/src/metrics.rs:6`, handler `crates/kbf-server/src/api.rs:66-72`, `docs/api.md:221`), served only on the optional operator listener `--api-listen` (`crates/kbf-server/src/config.rs:167-170`). The obstacle was reaching that listener, not authority, and it is the obstacle for the whole read API: every HTTP route is on that one plain-HTTP listener (8, "Today"). Every one of these becomes one API call below.

## 3. Entities, identity and links

| Entity | Id | Source | Links to |
|---|---|---|---|
| Invocation | client `tool_invocation_id` **[F]**; id-less calls are not recorded today (`crates/kbf-front/src/recorder.rs:17-19`, `minted: false` at `:450`); minting `kbf-<uuid>` is planned (`invocations.md` 2.3), not built | RequestMetadata (`crates/kbf-front/src/request_metadata.rs:103-119`) | actions; client report; commit |
| Action | action digest (sha256-size) | REAPI | runs, command, shape, result |
| Operation | REAPI operation name | scheduler | attempts; gone 60 s after it ends (`crates/kbf-sched/src/scheduler.rs:53`) |
| Attempt (lease) | `LeaseId`, shown `term.seq` (`crates/kbf-types/src/lease.rs:30`); v2 `epoch.seq` | scheduler | node, run record |
| Run record | `run_id`: 24 hex, time-ordered: 6 bytes of the commit time in milliseconds, 3 bytes of stream id, 3 bytes of row sequence in that stream. A stream is one (invocation, writer, day); id-less runs (Q12) use one stream per (writer, day), whose records live in the chunks of an id-less pseudo-invocation (below). The frontend mints the id from memory when the `Result` commits, so minting never writes to or waits on the state store: in U1 (no state store) the stream id comes from an in-process counter and the id resolves only through the in-memory recorder, so it is not durable and is never looked up after a restart (the time bytes keep ids of different runs of the server apart **[I]**); from U3 the stream id is taken from a block of 4,096 ids that the history writer reserves ahead of need from a C3 counter (`ui/streams`) in a background transaction, refilled when half used (a block lasts days at the assumed 1,000 invocations a day). If the block runs out before a refill commits (a starved background lane, 5.2, or a state store that is down), the frontend does not wait: it takes a fallback stream id from an in-process counter in a range no block uses (top bit set, the next 7 bits the writer's frontend index, 0 on the single frontend, so 65,536 ids per writer), not durable and reused after a restart **[I]**. Because the `ui/stream` row key carries the stream's first commit time (5.3) and a lookup takes the newest row of that stream id at or before the run id's time bytes, a fallback id reused after a restart still resolves to the right chunk. The history writer writes the `ui/stream` row after the commit, with the stream's first chunk. The id therefore locates its own chunk with no per-run index row (5.3) | new (5.2) | all per-attempt data; `GET /v1/runs/{run_id}` |
| Shape | 16-hex key, kbf#765 (`crates/kbf-server/src/action_usage/shape.rs:61-146`) | computed from the Command at Execute | `cfg` variants, targets seen, run and duration history |
| Test target | `(instance, shape, cfg)`; plus target label when known | shape + client | outcomes over time |
| Node | node id from `Hello` | daemon | leases, samples |
| Blob | digest | storage | `available` flag, retention |
| Commit, branch | client-supplied strings; commits have no order across branches | client report or header (4.6) | invocations; history is per branch (4.3) |

- **[F]** buck2 sends only `tool_invocation_id` (its Build ID) and `tool_details` (with a fixed version); `action_id`, `action_mnemonic`, `target_id`, `configuration_id`, `correlated_invocations_id` are empty (`crates/kbf-front/tests/request_metadata.rs:33-63`, golden `crates/kbf-front/tests/data/buck2-execute.requestmetadata`). Bazel fills them all, read from its source only, not captured on the wire **[V]**.
- **[F]** Shape key = first 8 bytes of SHA-256 over a version tag, the normalized program words (up to 3) and the sorted, deduplicated normalized output patterns; RequestMetadata never enters it, and `cfg` (the config hash taken out of output paths) is not part of it (`crates/kbf-server/src/action_usage/shape.rs:61-146`).
- **[F]** Known limit: a buck2 remote test's outputs sit under `buck-out/v2/test/execution/<cell>/<hash>/<hash>/`, the first hash covering target and configuration, the second the test-case set. Such an action keys once per target, configuration and test-case set, with `cfg=-` (`crates/kbf-server/src/action_usage/shape.rs:36-42`). **[I]** Good for history (stable across builds); it cannot name the target, and a changed test-case set starts a new key, so one test's history can span several keys. The target lookup and key links of 4.3 join them.
- **[F]** The key-to-shape mapping exists today only in `action shape:` log lines, deduplicated in memory; the dedup set is cleared when it reaches 65,536 entries (`crates/kbf-server/src/action_usage.rs:59-61`, `:100-145`). That is a memory bound on the log, not a bound on distinct keys. It must become catalog rows (5.3).
- **[I]** A cache hit carries no Command (buck2 uploads no Action for a hit), so its shape comes from the day index's digest section of a day that digest executed, or carried it forward (4.2, 5.3).
- **[D]** Id-less runs: once history keys outcomes by instance and shape, an id-less run still produces a test outcome with a null invocation (section 10 Q12); today such a run leaves nothing.
- **[I]** Where an id-less run lives (from U3; before U3 it is not recorded and gets no `run_id`, as today). Each (writer, day) has one **id-less pseudo-invocation** with `inv-key` = first 16 hex of SHA-256 of `idless/<writer id>/<day>`, a string no client id can produce because a recorded id is hashed as `id/<record id>`. Its run and hit records, tails, command renderings and failed-run sections go into chunks under that key like any invocation's (5.3), with the same flush rule, its own `ui/stream`, `ui/ichunk` and `ui/invid` rows (the header marked `idless`, holding counters and the instances used), so `/v1/runs/{id}`, the day-index digest and node sections, pins and the purge rewrite reach them by the same path. It writes no `ui/inv` or `ui/invc` list entry, so it never appears in `/v1/invocations`; `/v1/invocations/{id}` cannot name it (it has no client id); a run's envelope (6.3) says `invocation: null`, and its outcome's invocation is null.

## 4. Items: fields, source, retention, API

Each subsection: fields, source today **[F]** or what to add, retention and size, the route (section 6 lists all routes; "built" means it exists at HEAD).

**Rates used for sizes [I].** Daily volume: about 4 operations a second, the pilot rate assumed in the comment on `FINISHED_RETENTION` (`crates/kbf-sched/src/scheduler.rs:50-52`, cited by `invocations.md:246-247`), not a measurement: about 345,600 executions a day. Burst: 300 actions a second (`architecture-v2.md` 4.1 C7). Cache hits: executions x h/(1-h) at a stated hit rate h, sized at h = 0.9 (9 hits per execution) unless a line says otherwise **[V]**. Index overhead: every indexed row is sized at 1.5 x its raw bytes **[I]**.

**Attempts with no logs [F].** A memory-killed, lost or infra attempt has no stdout or stderr: the daemon's `failure()` sets `action_result: None` (`crates/kbf-daemon/src/lease.rs:351-360`), and `carry_usage` then adds a default `ActionResult` holding only usage (`lease.rs:313-316`). Such an attempt's `logs` key is absent (not measured, 6.1), so an agent does not wait for a log that never existed; its reason text and the usage block are what it has.

**Logs and their lifetime.** **[F]** stdout/stderr always go to the CAS by digest, capped at 1 GiB per stream (`crates/kbf-outputs/src/limits.rs:19-35`). Read by `GET /v1/blobs/{digest}` with one Range or `?inline=text` up to 4 MiB (`crates/kbf-server/src/http_blobs.rs:15-25`, `:155`). Retention policy is 7 days after last touch plus a 1-day quantum (`crates/kbf-meta/src/model.rs:178-202`), but the server never runs collection (no caller of `Cache::collect` in `crates/kbf-server/src`), so on S3/MinIO a log is kept forever, and on a `file://` cold store the evictor can drop it 60 s after last use under disk pressure (`crates/kbf-storage/src/cache/evict.rs:27-30`). **[F]** A failed run's ActionResult is in the CAS but not in the AC (only exit 0 is cached, `crates/kbf-server/src/farm.rs:1142`), so nothing indexes it once the record is gone. The run record is that index.

**Tails in the record [I].** A failed or timed-out run's last 16 KiB of stdout and of stderr, after operator redaction (8), are stored with its record in the failed-run section of its invocation chunk (5.3), so cross-build lists and `/failures` past the live view serve tails from chunk objects and never read log blobs. The history writer reads them after the commit, off the acknowledgement path, under its own share of the read budget, and skips a log over 64 MiB (`tail_omitted: "too_large"`) **[V]** (alternative: the daemon carries the tails in `auxiliary_metadata`). Arithmetic: 3,456 failed runs/day x 32 KiB = about 113 MB/day raw in chunks (5.3). A tail stored is redacted with the patterns in force when it was written; a leak found later is purged (8).

**Pins for failures [D] (Q5).** Pin a failed or timed-out run's stdout, stderr and ActionResult for 30 days within a byte budget (`--failure-pin-bytes`, default 20 GiB). Client reports never count against it: they are history objects, not pins (4.6). **Per-instance shares**: each instance gets a share of the budget (a policy key; default the budget divided by the instances with a pin in the last 30 days), and eviction drops the oldest pin of the instance furthest over its share first, so one instance's noisy failing suite evicts its own pins, not another's. The Command is not pinned as a raw blob: its decoded, redacted rendering (argv after redaction, env names only, at most 16 KiB) is stored in the chunk's failed-run section (8). **Per-run cap**: a stream over 16 MiB is not pinned and shows `pinned: false, pin_skipped: "too_large"`; one run therefore pins at most about 32 MiB, so failure pins always keep at least 20 GiB / 32 MiB = 640 failed runs farm-wide, and at least share / 32 MiB per instance; a bad build of huge logs evicts only its own instance's pins beyond that. Arithmetic **[I]**: at a 1% failure rate, 3,456 failed runs/day; at 64 KiB of logs each, 221,184 KiB = 226 MB/day, 6.8 GB for 30 days; command renderings at about 4 KiB each, 14 MB/day, 0.42 GB for 30 days. Failure rate and log size are **[V]**. How storage honours a pin is 5.4; nothing in storage does today. Q21 asks whether 30-day copies into the object store replace the pins.

**Run record size [I].** Ids and digests (run id 12, invocation ref 8, action 40, result 40, command 40, input root 40, stdout 40, stderr 40) 248 B; nine REAPI timestamps plus `granted`, 10 x 8 = 80 B; instance ref 4, shape 8, cfg 8, node ref 4, lease 16, exit code, outcome, memory kill 8; booked and raised 16; wait reason and partition 8; farm runs/budget 2; presubmit 4; cgroup 10 counters 80 B plus NUMA (2 nodes) 16 B; transfer 6 counters 48 B; about 560 B raw. Its outputs listing (about 2 a run, 44 B plus a 60 B path) rides in the same record: about 770 B a run in its invocation chunk, 266 MB/day raw. There are no per-row indexes: lookups by action digest, by shape and by node use sections of the day index object (5.3) of 49, 47 and 35 B an entry, about 45 MB/day together.

**Cache-hit records [I].** A hit has no run, but `/actions` lists it today. Its invocation chunk keeps a hit record: instance 4, invocation ref 8, action digest 40, `how` 1, time 8, about 60 B; no output listing, because the ActionResult in the AC holds it. At h = 0.9: 3,110,400 hits/day, 187 MB/day raw (h = 0.67: 42 MB). A hit on a test shape is also referenced (36 B) in the window and day index, for grid cells and `last_cached_pass` (4.3).

**Attributing a hit to a shape [I].** A hit record carries no shape, but the daily rollup counts `cached` per (instance, shape, cfg, branch). The history writer resolves each hit's digest, in order: an in-memory LRU (at most 100 MB); today's in-memory day index; then older day-index digest sections, newest first, whose blooms skip days without the digest, so a probe costs about one block, usually from the local cache (5.5). A digest resolved from a section older than 15 days is carried forward into today's section, so a digest served only from cache keeps resolving for as long as it is hit, at most about 1,000,000 / 15 = 67,000 entries a day, about 3.3 MB, at an assumed 1,000,000 distinct digests hit a day **[V]**. The writer keeps per-(day, instance, shape, cfg, branch) counters in memory and writes the deltas of changed keys into each 120 s window object (5.3), so with a healthy object store a crash loses at most 120 s of counts (5.2); the single frontend adds its unwritten deltas to a rollup read, and with several frontends (P9) a read lags by at most one window. The same resolution keeps today's `last_cached_pass` per test key in memory and in each window; it reaches the status rows only at day close (4.3).

Routes: `GET /v1/invocations/{id}/actions` and `/actions/{digest}` (built; built fields unchanged, new keys added, new filters `requeue_reason=`, `memory_kill=`, new `sort=`); `GET /v1/invocations/{id}/failures` (planned PR 12, `invocations-api.md`); `GET /v1/runs/{run_id}` (new: one attempt); `GET /v1/runs?node=&from=&to=&class=&instance=` (new: runs by node and time, paged, instance-scoped as in 8); `GET /v1/actions/{digest}/runs` (new: every run of a digest across builds the caller may read); `GET /v1/commands/{digest}` (new); `GET /v1/blobs/{digest}` (built).

### 4.3 Shape and test history

**Every shape has history.** Duration trends and runs by key exist for every shape, so a compile or link that slows across builds (its digest changes with the code, its shape does not) is answerable: `/v1/shapes/{key}/daily` gives the trend, and `/v1/shapes/{key}/runs` lists the runs behind it (run id, digest, invocation, node, execution time) for any shape within the 30-day run tier, so the digest and commit where it slowed and the nodes that ran the slow ones are one more call. Past 30 days only test shapes keep per-run records (outcomes); other shapes keep their daily rollups. Tests are a filter.

**What a test is to the farm [I].** An action whose shape marks it a test: a buck2 output under `buck-out/v2/test/execution/`, or a Bazel `action_mnemonic` of `TestRunner` with a `target_id`. Its key is `(instance, shape, cfg)`; `target` is attached when Bazel names it or a client report maps the key.

**From a target to its keys.** An agent knows a test by its target label. `GET /v1/shapes?target=<label>&program=` returns every `(shape, cfg)` key mapped to that target, with first and last seen; `/v1/shapes/{key}` carries `previous_keys` and `next_keys` when reports map two keys to the same target (a changed test-case set or configuration). Without any report or Bazel `target_id`, the link is unknown, and the answer says `target: null`.

**Outcome per run** (separate infra from test, as ResultDB and TestGrid do):

| Status | Rule |
|---|---|
| `passed` | ran, exit 0 |
| `failed` | ran, non-zero exit (Action class) |
| `timed_out` | Timeout class |
| `infra` | Infra, lost, node pressure, missing input; excluded from flakiness and first-failing math |
| `oom_rung` | an own-limit memory kill followed by a ladder rung; not a test result |
| `oom_killed` | an own-limit memory kill with no rung left (`memory_kill: own_limit`, no requeue): the attempt that ends the operation. Counts as a failure for `first_fail`, transitions and `status`: the action does not fit the farm's largest node, and the cause is the action, not the farm |
| `cached_pass` | an AC hit on a test shape's digest (only exit 0 is cached, so it is a pass, `source: cache`); counts as a pass for `status`, `last_pass`, transitions and grid cells, never for the digest rule (it adds no new digest observation) |
| `preempted` | an idle-band run killed for real work (7); not a test result |

A cache hit on a test is not an outcome record, which keeps outcome volume independent of h, but it is an observation. The history writer, which already resolves each hit to its shape (4.2), keeps today's newest `last_cached_pass {commit, invocation, at, digest}` per (instance, shape, cfg, branch) in memory and writes it into each 120 s window's test-shape hit references; status, `last_pass` and transitions read the status row plus that in-memory value (and, with several frontends, the peers' windows of today, lagging at most one window), and after a restart today's values are rebuilt from today's windows (5.2). The status row's own `last_cached_pass` is written only by the day-close fold, at most once per key per day, so cache hits add no row writes through the day. A per-window row update would cost far more: about 622,000 test-shape hits a day (20% of H) touch up to a few hundred keys per window, about 0.2 to 0.6 million row writes a day, and at the burst (about 540 test-shape hits a second) up to the 100,000-row status bound per window, beyond the index write cap of 5.2. Without it a fix served from cache (a revert that restores a digest that passed before, the usual case on a cached farm) would leave `status: failing` and `first_fail` at the broken commit for ever. Grid cells read `cached_pass` from the day index's test-shape hit references for their column's invocation within 30 days, and from the daily rollup's `cached` count beyond (Q15). Volume: about 80 B in each status row, at most 100,000 rows.

**Derived per `(instance, shape, cfg)`:**

- **Flaky, proven.** `failure-classes.md` 6.3 (decided): one action digest seen both passing and failing is flaky, a lower bound because a pass is cached. Computed as outcomes arrive: each key's status row (5.3) keeps the verdicts of its last 16 digests, and a digest seen both ways sets `proven` with `proof_digest` and `since`, which stay set; this holds after run records expire. **[I]** A narrowing of a 400-day scan: a digest older than the key's last 16 is no longer the code under test. Outcome objects keep the digest for 400 days, so a proof can be re-derived. The answer names `proof_digest` and links its runs.
- **Flaky, possible.** An ambiguous run followed by a pass (6.3 case 3; the planned `kbf_possible_flaky_digests`, `failure-classes.md:906`).
- **Per branch.** Transitions, `flaky.since`, `last_pass` and `first_fail` are computed per branch, over outcomes whose invocation carries that branch (4.6), defaulting to a configured default branch (`--history-default-branch`, default `main`). Commits are opaque client strings, so they have no order across branches; a work-in-progress build that breaks a test on branch X never moves the default branch's `first_fail` or `flaky.since`. Outcomes with no branch count only toward the digest rule (proven flaky), which is branch-independent.
- **Transition score (hint).** Pass/fail transitions over the last N non-infra runs of one branch, ordered by commit time when known, else by time (the Buildkite transition count).
- **Flaky since.** The first non-infra transition, or the first digest seen both ways, inside the window: `{commit, invocation, at}`. Unlike `first_fail`, it does not move when the test passes again.
- **First failing commit.** The earliest commit after the last pass in the ordered history; without commits, the first failing invocation and its time. **[F]** No commit is in any REAPI field; it needs 4.6. Kept in the status row as outcomes arrive; outcome records carry a commit ref, so it holds over 400 days.
- **Duration trend.** p50/p90 of execution time (from the copied timestamps, not wall incl. queue) per day, for every shape.

**Source today.** **[F]** None: the record is in memory, cross-build queries are out of the invocations plan (`docs/design/invocations.md:444-453`), and no flake table or `/v1/flakes` route exists (section 0).

### 4.5 Metrics over time

- **[F]** `/metrics` resets at process start; only `kbf_meta_commit_seconds` has a label (`crates/kbf-storage/src/metrics.rs:649-657`); no daemon serves metrics; no scrape or time-series config exists in the repo. Two counters are kept but exported nowhere: `kbf_invocation_metadata_invalid` and `kbf_invocation_events_dropped` (`crates/kbf-front/src/request_metadata.rs:232`, `crates/kbf-front/src/recorder.rs:190`).
- **Two paths, one source.** Labeled families on `/metrics` (by platform, QoS, node, outcome class) for an operator's Prometheus; and a small built-in rollup of a fixed series set in history objects (5.3), so the owner's health view works with no external system.
- **Fixed series set** (from `architecture-v2.md` 11 plus the questions of 2.1): queue depth and oldest age by partition; claim wait p50/p90; leases; idle CPUs and memory per node; busy CPU fraction; executions, cache hits, failures by class, farm reruns, OOM rungs per minute; failures by class per node (4 classes: action, timeout, infra, memory); hot-store fill; flush lag; under-replicated and lost blobs; group-commit latency; history writer drops and queue fill.
- **Downsampling per series kind.** A mean is wrong for most of these: a mean of minute p90s hides one bad minute (one 60 s minute among 59 at 1 s averages to about 2 s), and a mean of a gauge hides the peak W2 and O2 ask about. So each series has a kind. **Counters** (executions, hits, failures, reruns, OOM rungs): a point is the sum over its interval; an hour sums its minutes. **Gauges** (queue depth, oldest age, leases, idle CPUs, fill, flush lag, under-replicated, lost blobs): a point is min, mean and max; an hour takes the min of mins, mean of means, max of maxes. **Latency** (claim wait, group-commit latency): a point is a fixed-bucket histogram (16 buckets x 4 B); an hour adds its minutes' buckets, and p50/p90 are read from the merged histogram, within one bucket's width.
- **Node samples** (booked, free, lease count, phase, pressure, CPU busy; 20 numeric fields) every 15 s, stored as binary records (20 x 4 B, a time and a node ref: about 92 B) in window objects and then the day index's node-sample section, kept as long as run records (30 days), read by `GET /v1/nodes/{id}/samples?from=&to=` (paged). Each run's `node` links there with `from` and `to` set to the attempt's times, so "slow because of the node" is one call for the whole life of the run record.
- **Sizes [I].** Built-in: 40 series plus 8 nodes x 10 per-node series (6, plus 4 failure counters) = 120 series, assumed 62 counters, 54 gauges, 4 latency; a point is an 8 B time plus 8 B (counter), 3 x 8 B (gauge) or 64 B (histogram). 1-minute points (1,440 a series a day): 62 x 1,440 x 16 B + 54 x 1,440 x 32 B + 4 x 1,440 x 72 B = 1.4 + 2.5 + 0.4 = 4.3 MB a day in daily objects, kept 45 days (about 0.2 GB); hourly for 400 days (9,600 a series): 9.5 + 16.6 + 2.8 = 29 MB in monthly objects. Node samples for 30 days: 8 x 5,760 x 30 x 92 B = 127 MB (as 0.5 KiB JSON it would be 708 MB). An external Prometheus over about 1,000 series at 15 s and about 1.5 B a sample stores about 8.6 MiB/day.
- Route: `GET /v1/series/{name}?from=&to=&step=&labels=` (new); `GET /v1/series` lists names, units and retention.

### 4.6 Client report (what REAPI cannot carry)

**Display only (section 1).** Everything below is shown beside the farm's own data and labelled as client-reported. It never becomes a key: not for target identity (derived from output paths, #796), not for first failing commit or branch history (farm-fetched commits only), not for flakiness (digest outcomes only).


- Route: `POST /v1/invocations/{id}/report`, body one of: a buck2 build report (`--build-report`), buck2 `log what-ran --format json`, buck2 `log critical-path --format json`, a JUnit XML file per test, and a small JSON of `{commit, branch, repo}`. Bazel BES is later.
- **Who may write.** A caller whose `public` metadata equals the record's `owner` (`invocations.md` 2.4), and, once read tokens exist, not a `read` role. A different owner's report goes to its own `<id>~<n>` record, as its calls would, and never changes the first record's commit or target map. **[F]** The owner check means something only under a per-caller authenticator: `owner` is the caller's `public` metadata (`crates/kbf-front/src/recorder.rs:470-475`), an `allow` authenticator gives every caller the same fixed metadata (`crates/kbf-auth/src/policy.rs:280-290`), and with no policy file every caller's metadata is empty (`invocations.md:170-172`), so under either every caller owns every record. Hence the route is off unless the policy authenticates callers (8).
- **Bounds.** At most 32 MiB per report and 16 reports per invocation; over either, `413`. A per-owner quota (bytes a day, a policy key, default 1 GiB) on top; over it, `429`. Reports are stored as compressed history objects (`r7/report/...`, 5.3) kept 7 days by their class's expiry, not in storage and not pinned, so a report never evicts a failure log. Volume **[I]**: a 9,000-action build's `what-ran` is about 2.7 MB at 300 B a line, plus a build report, about 3 MB an invocation; at the assumed 1,000 invocations a day, about 3 GB a day raw, about 0.5 GB stored **[V]**, 3.5 GB for the 7 days. The joins that matter (commit, branch, target per shape) are copied into index rows, and test cases into `r30/tests` objects, when the report is posted, and outlive it.
- Gives: commit (first failing commit), target names per shape (joined by the action digest or output path in `what-ran` **[V]**), critical path, test-case results.
- Read back: `GET /v1/invocations/{id}/report` (the stored reports, with links) and `GET /v1/invocations/{id}/tests` (parsed test cases joined to shape and run, paged); a failed test action's entry in `failures` carries `cases_href`.
- Alternative for the commit alone: a header the client sends on every call. **[V]** whether buck2's RE client config can add a header from the environment.
- Size **[I]**: a 50,000-action `what-ran` at about 300 B a line is 15 MB, which is why only the joins (target per shape, commit) are copied into index rows.

### 5.2 Where it lives

**The rule [D].** The object store is the truth for history; the tables are an index that can be rebuilt from it. Bulk data is immutable objects under `<prefix>history/`: run and hit records, outputs listings, tails, command renderings, window data, day indexes, outcomes, rollups, series, events, catalog deltas, invocation summaries and reports. The **metadata store** holds only small rows that point into those objects or are hot aggregates: invocation headers and their chunk lists, the shape catalog, target map and per-shape status, pins, and the object catalog the store contract requires. Losing it costs a rebuild by listing `history/`, never a record: the "derived index, never authoritative" of `invocations.md` 3.7, built.

- **[F] What the object store offers.** `ObjectStore` has `put_new(key, body, retain_until)`, `get_range`, `may_hold`, a retry-safe `delete` and `list`, documented "for rebuild and the weekly sweep only"; `Capabilities` claims `conditional_put` and `object_lock`; S3, local-directory and in-memory backends pass one conformance suite (`crates/kbf-objstore/src/lib.rs:1-89`, `crates/kbf-objstore/src/types.rs:264-273`). The contract: kbf "never asks a store whether something exists, and needs no consistent listing and no read-after-write", because it records every key itself (`lib.rs:5-9`). So every history object is recorded in the metadata store before anything relies on it.
- **[F] Keys today** are `<prefix>cas/<epoch>/<seq>` (`crates/kbf-storage/src/cache.rs:325-331`) under the default S3 prefix `kbf/` (`crates/kbf-server/src/stores.rs:39`); `history/` collides with nothing.
- **Object store interface.** The existing `ObjectStore`, unchanged, plus a `Scoped<S>` wrapper that refuses any key outside its prefix. `--history-objects=<URI>` names it; the default is the cold store under `<prefix>history/`.
- **Metadata store interface.** A `ui/` key namespace on the `kbf-state` trait, so every backend that passes the state-store suite serves it (`architecture-v2.md` 4.1). `architecture-v2.md` section 1 (the frontend bullet) is amended in the same commit as this text to say so: a frontend's durable state is the state store (scheduler and index rows) plus the object store (history). Why not a database of its own: index writes average about 1.5 rows a second through the day and at most about 80 at the burst (derived below), about 5% of C7's 1,500 writes/s, and they share a batch with a `Start` or `Result` only after aging, one at a time and behind them (the background lane below), so the commit-budget and WAL reasons for a separate store are gone. **[F]** One method is missing: `scan_prefix` returns every key under a prefix, unbounded (`crates/kbf-state/src/store.rs:28-33`), and paged index reads need a bounded range scan; Q20 proposes `scan_range(start, end, limit, reverse)` under a new suite clause C8, ordered as C5's scan. `--history-index=<state-store URI>` puts the index on a second instance of the same trait for an operator who wants isolation, a configuration choice with no new code; pins and the purge tombstone stay in the state store either way (5.4, 8).
- **The background lane.** A transaction of its own is not a batch of its own: `Store::apply_batch` feeds concurrent `Store::txn` calls through one path with one sync per batch (**[F]** `crates/kbf-state/src/store.rs:13-19`), and SQLite has one writer thread (`architecture-v2.md` 4.3), so an index transaction could share a group commit with `Start`/`Result` transactions, or be applied ahead of them, and lengthen their commit, which is the acknowledgement path. **[F]** `Txn` has no priority today (`crates/kbf-state/src/types.rs:97-99`). So the trait gains a background mark on a transaction, and every backend must honour it: a background transaction is applied only in a batch with no foreground transaction waiting, or once it has aged (next item), at most one per batch, never ahead of a foreground transaction queued before the batch is cut, and is at most 256 rows or 256 KiB (SQLite: the writer thread takes from the foreground queue first; Postgres: background transactions use their own one-connection pool, so they never hold a connection a commit waits for). The history writer sends at most 2 a second, so at most 512 rows a second. This is written into suite clause C7 (`architecture-v2.md` 4.1, amended in the same commit as this text), so a backend admitted later meets it too: the C7 load test runs with background transactions at that cap beside 1,500 foreground writes/s, `Result` commit p99 stays within the C7 bound, and the background rows are applied at the cap (next item). An operator on SQLite who wants the index off the writer thread altogether uses `--history-index=sqlite:///<second file>`.
- **Background progress.** "No foreground transaction waiting" alone could starve the index: at C7's burst (1,500 foreground writes/s, 5 ms batches) a new foreground transaction arrives while nearly every batch syncs, so an idle batch may never come. So C7 also bounds the wait: a background transaction that has waited 250 ms or 16 batches, whichever comes first, joins the next batch anyway, still alone among background transactions and placed after every foreground transaction in that batch. **[I]** That gives at least 4 background transactions a second, 1,024 rows a second at 256 rows, against the writer's cap of 2 a second (512 rows); its cost to a foreground commit is the rows written inside a batch's one sync, never an extra sync, in at most 2 batches a second of about 200. The C7 load test asserts both sides: `Result` commit p99 within the bound, and background rows applied at no less than the offered 512 rows/s over the run, with the backend's background queue bounded; a planted backend that never applies a background transaction while foreground load continues goes red on the second assertion.
- **Pending index writes, bounded.** The writer holds index writes not yet applied in memory, coalesced per key (a second write to a row replaces the pending one), at most 131,072 keys or 32 MiB **[I]**. Past either, a new write is dropped and counted under `stage="index"`; nothing waits. No record is lost: a dropped pointer row (`ichunk`, `stream`, `obj`, list entries) names an object already PUT, and the writer keeps that object's key (it chose the key itself; about 100 B each, a separate list bounded at 65,536 keys, past which the oldest falls to the weekly sweep) and re-inserts the row from the object's header and footer when the backlog drains, so the row returns within the drain time with no LIST, which the object-store contract above does not offer for this; a dropped header write is replaced by the invocation's next chunk; a dropped `status` write is restored by that day's close, whose fold recomputes every key that had outcomes that day from the day's outcome object. A `ui/streams` refill is a write like any other and may wait or drop; minting then uses the fallback stream ids of 3, so `run_id` minting never waits on this lane.
- **A pure crate `kbf-history`** (no runtime, as `kbf-segments`): object formats, key naming, retention classes. The writer and reader live in `kbf-server`.
- **Written after commit.** The frontend enqueues a run event after the `Result` commit, and a hit event after the answer. A bounded queue (131,072 events or 64 MiB, whichever first: one 9,000-execution build with its hits, about 90,000 events and 20 MB, fits with the writer stalled) feeds per-invocation chunk buffers (inside `--invocation-memory`), the current window and today's in-memory day index. A full queue drops and counts. History never delays a build; losing it loses records, never results.
- **Object first, pointer second.** PUT the object with `put_new` (keys are never reused, so `AlreadyExists` on a retry is success); then, in one transaction, insert its index row with `Cond::absent` and upsert the invocation header. Never the reverse. A crash between the two leaves an orphan object, expired by its class or adopted by the weekly sweep; objects describe themselves (the header names family, writer, day and sequence; the footer carries the summary), so adoption is idempotent.
- **When objects are cut.** An invocation chunk at 256 KiB raw, when the invocation turns idle, or 120 s after its oldest unflushed record (the rule of `invocations.md` 3.4, kept). A window object every 120 s. Day index and daily objects at day close (00:10 UTC), merged from that day's windows, under a `ui/job/<name>` lease row (C1 with a C4 TTL); a partial day index (`-p<n>`) if today's in-memory index passes 256 MiB. Monthly objects on the first day of the next month.
- **Crash [I].** Loses everything not yet in an object: the event queue (at most 131,072 events or 64 MiB, about 44 s of burst) plus every unflushed chunk buffer (at most `--invocation-memory`) and the open window. With a healthy object store a buffer is flushed within 120 s, so that is the usual bound; while the store is slow or down buffers are held up to their memory bounds (below) and a crash then loses all of them, however old. On restart every invocation that was open says `complete: false` with `gap_from` the time of its last successful chunk PUT, which may be much older than 120 s; today's day index is rebuilt from today's windows (at most 720 GETs, about 60 MB) plus chunks written after the last window, and until that is done the cross-build routes answer `503` with `Retry-After`.
- **Object store down.** The writer retries with backoff and holds buffers inside their memory bounds; past them it drops the oldest buffer and its invocation says `complete: false`. An index write that fails after a successful PUT is retried, then counted, and its object key joins the same re-insert list as a dropped pointer (Pending index writes, above); the weekly sweep adopts only what fell off that list.
- **Drop accounting.** `kbf_history_dropped_total{stage="queue|buffer|put|index|tail"}`; the `index` stage loses no record, because the object holds it. Queue fill and drops are series (4.5).
- **Several frontends (P9/P10).** Each frontend writes only its own keys (the writer id is in the key: the server epoch in v1, (member id, boot counter) in v2), so no object is shared and nothing races. The day and month jobs run under the lease row. Each frontend reads its peers' windows, so a cross-build read lags by at most 120 s. `--history-objects=file://` with a Postgres state store is a usage error: a file store would be durable local state.
- **Credential boundary.** `architecture-v2.md` 9 gives cold-store credentials, in isolated-storage mode, to storage nodes only. Frontends write `history/`, so they hold a credential limited to that prefix (or to a separate bucket named by `--history-objects`), never one that reads or writes `cas/`. The boundary is the credential, enforced by the object store, so the proof is at that layer. Red test (U3, in the `kbf-it` cell against MinIO, `crates/kbf-it/src/m1.rs`): an `S3Store` built from the credential the frontend is configured with fails a raw GET and a raw PUT of a `cas/` key with access denied, and succeeds on a `history/` key; the same test with the cold-store credential goes red, which shows it can fail. **[V]** that the cell can create a prefix-scoped MinIO user (else the test uses a second bucket). The history writer's `Scoped` store also refuses a `cas/` key; that is defence in depth against a kbf bug, not the proof, because a frontend given the full credential would still pass it. v1's single server holds the cold-store credential already.
- **Index load on the state store [I].** Row operations per family, at the rates of 4 and 5.3 (E, H, T, 1,000 invocations a day); "per window" writes coalesce every change to one row within a 120 s window into one write.

### 5.3 Objects, index rows, retention and cost

**One container format for every family.**

```
header : magic "KBFH", version u16, family u8, writer id, day, seq, base time (ms)
blocks : zstd, each <= 64 KiB raw, length-prefixed protobuf records, sorted by the family's key
footer : block index (first key, offset, len, records, crc32c); a bloom filter per keyed
         section (10 bits/key); family summary
trailer: footer offset u64, footer len u32, crc32c, magic (24 B)
```

The footer's offset and length are kept in the object's index row, so a footer is one exact range GET; **[F]** the segment format needs two, the trailer and then the footer (`crates/kbf-segments/src/layout.rs:99-104`). Segments are the model, not the container: they are indexed by digest, and history is looked up by composite keys. Footers are cached in memory and on disk (5.5).

**Keys** are `<prefix>history/<class>/<family>/<yyyymmdd written, UTC>/...`. The retention class leads, so one lifecycle rule covers a class; the day lets the sweeper delete whole days.

**Families [I].** Rates as in 4: E = 345,600 executions, H = 3,110,400 hits, F = 3,456 failed runs, T = 69,120 test outcomes and 1,000 invocations a day. Stored sizes assume about 2x from zstd **[V]**.

**Requests and cost [I].** Prices are S3 Standard list prices **[V]**: PUT $0.005 per 1,000, GET $0.0004 per 1,000, $0.023 per GB-month; DELETE and lifecycle expiry are free.

- **GETs, about 46,000 a day, about $0.018 a day ($0.55 a month):** day close 720, monthly jobs about 100, a restart at most 1,000; reads about 44,000, from an assumed 22,000 API calls a day at 2 uncached GETs each **[V]**; hit resolution about none at steady state (local cache). The 2 is an assumption about the call mix and the cache, not a route figure: most calls are summaries, lists and shape or status reads (index only, or 1 GET), and most `/actions` and `/failures` reads are of builds under a day old, whose chunks the cache holds (5.5); a cold `/actions?sort=` is 23 to 80 GETs and `/shapes/{key}/daily` up to 44 (5.5). Sensitivity: at 10 uncached GETs a call, about 222,000 GETs a day, $2.7 a month; at 40, about 882,000 a day, $10.6 a month. The GET count per route and the cache hit ratio are U3 metrics, so the real figure is measured, not assumed.
- **LIST:** about 500 pages a week for the sweep.
- **Stored:** about 18 GB, about $0.41 a month (21.5 GB with Q21, about $0.49).
- **Total about $3.1 a month** ($2.12 PUT + $0.55 GET + $0.41 stored), **about $3.7 with Q21** ($2.64 + $0.55 + $0.49), at 2 uncached GETs a call; add the sensitivity above if the cache misses more. The gain is operational, not cost: a 0.5 GB index in background transactions, no history database with WAL and checkpoint gates of its own, and frontend disk that is a cache.
- **Burst** (300 executions/s, 2,700 hits/s): about 0.5 MB/s raw into chunks, about 2.5 PUTs a second (S3 allows about 3,500 a second per prefix); today's day index grows about 46 KB/s in memory, capped by the 256 MiB spill.

### 5.4 Pins in storage

**[F]** No storage-side pin exists. The `file://` evictor drops a blob 60 s after its last use under disk pressure (`crates/kbf-storage/src/cache/evict.rs:27-30`), and the only pins in `kbf-meta` and `kbf-storage/src/cache` are pending touches held until `Cache::collect` commits them (`crates/kbf-storage/src/cache/touches.rs:11`). A `pin` row holds nothing on its own.

**Design (a): a pin set storage consults [I].** Chosen over (b), copies into a retained namespace, because (b) doubles the bytes of every pin and needs its own reads and purge path. With history objects in place (b)'s read and purge paths exist, which is why Q21 asks again.

- **Owner.** The `ui/pin/<digest>` rows (instance, kind `failure`, until, bytes) are written by the history writer into the state store, even when `--history-index` puts the rest of the index elsewhere; the cache crate (`kbf-front` cache today, `kbf-storage` in v2) owns an in-memory `PinSet` of digests, loaded from those rows at start and updated by the writer (an in-process call on the single frontend). Size **[I]**: about 3,456 runs x 3 digests (stdout, stderr, result) a day for 30 days, 311,000 digests, about 19 MB of memory at 60 B each. Client reports are history objects (4.6) and take no pin.
- **v1.** The evictor (`cache/evict.rs`) and `Cache::collect` skip a digest in the `PinSet`. Pinned bytes count against the disk the evictor protects, so the failure-pin budget (20 GiB) must fit under the cache's free-space target; the server refuses to start when it does not **[V]**.
- **v2.** The hot store may drop a blob once it is flushed (the cold store has it), so the owner's hot-tier eviction needs no change. Cold-store retention and segment compaction (neither built, 8 Purge) must skip pinned digests; they read the same `ui/pin/` rows through the state store **[V]**.
- **Expiry and purge.** A pin past `until`, or evicted by its budget's rule (4.2), is dropped from the rows and the set; purge drops the pin first (8).
- **Phase.** Pins land in U3 with history, before the pages of U6. Red test (U3): on a `file://` cold store under disk pressure, after the evictor runs, a pinned failed run's stderr is still readable from `/v1/blobs` and an unpinned blob of the same age is not.

## 6. Read API

### 6.1 Rules

- **The UI uses only this API.** A page is server-rendered from these JSON documents (PR #751's direction: embedded assets, no client toolchain **[I]**). Each page shows the URLs it read. A contract test lists, per page, the API calls it makes and fails if a page reads anything else.
- **Link forms, as built.** **[F]** Three forms, all root-relative strings. (1) A link to one object (a blob, an action) is under the key `href` (`/v1/blobs/{digest}?instance=..`, or `/v1/invocations/{id}/actions/{digest}`), and a blob link is `null` when the blob route is off (`crates/kbf-server/src/http_invocations/views.rs:40-81`, `:152`, `:169`; `pages.rs:521`). (2) The invocation summary's links to its sub-routes are the string values of its `links` map, `{"actions", "artifacts", "logs", "metrics"}` (`views.rs:123-128`). (3) A paged answer's next page is `next_page` (`pages.rs:584-585`). `invocations-api.md` 4.8 has the client rewrite exactly these: every `href`, every `links` value and `next_page`. **New links keep those forms.** A new sub-route of the invocation is a new key of the summary's `links` map, a flat string like the built ones: `failures` (as `invocations-api.md` 4.7 already shows), `critical_path`, `report`, `tests`, `events`. Every other new link is `href`, or `<name>_href` beside other keys of one object (`outputs_href`, `tree_href`, `runs_href`, `proof_runs_href`, `node_samples_href`, `cases_href`); the per-reason rerun lists of the summary are such objects, `reruns: [{"reason": "out_of_memory", "actions": 3, "href": "/v1/invocations/{id}/actions?requeue_reason=out_of_memory"}]`, not `links` keys, because a `links` value is one string and the set of reasons is open. New paged routes answer `next_page` as built. Every link is root-relative, and a client resolves it against the listener it read the document from; a link whose route reads blob bytes (`/v1/blobs`, `/v1/commands`, `/v1/trees`) is `null` when the blob route is off, as built. `kbf build show <href>` (`invocations-api.md` 4.8) reads any link, so the CLI and the UI see the same documents. Every run anywhere (an attempt in an action, an outcome, a grid cell, an entry of `actions/{digest}/runs`) links to `GET /v1/runs/{run_id}`. A run returned outside its action's page carries the envelope of 6.3 (invocation, instance, action, command, result, outputs), so an agent arriving from a grid cell or a flaky shape can reach the build, the command and every output in one more call.
- **Index.** `GET /v1` returns every route with its parameters, units, retention and authority; `GET /llms.txt` is the same as plain text for an agent with no prior knowledge.
- **Paging** as built: `page_size` (default 100, max 1000) and opaque `page_token` (`crates/kbf-server/src/http_invocations/pages.rs:16-19`, parsing at `:224-235`). Filters are query parameters; lists are newest first unless `sort=` says otherwise.
- **Built fields keep their form.** **[F]** Built times are RFC 3339 strings (`queued`, `granted`, `started`, `ended`, `views.rs:309-317`), the lease is `term.seq`, the node is `worker`, an attempt's end is `{"result": "ok"}`, `{"requeue": ..., "reason": ...}` or `{"failure": ..., "reason": ...}` (`views.rs:298-307`). New timestamps use the same RFC 3339 strings; new durations and sizes carry units in their names (`_us`, `_ms`, `_bytes`). Absent means not measured, never zero. A rename would be a breaking change with a version bump; none is proposed.
- **Gone data says so.** `available: false` for a blob; `410` with the retention that expired it for a record past its tier.
- **Tails** on every route returning the run shape follow `invocations-api.md` 4.7: 16 KiB, no tail over 64 MiB (`tail_omitted: "too_large"`), `tail: null, tail_omitted: "busy"` when the read budget is not free within its wait. From U3 a failed or timed-out run's tails come from the failed-run section of its invocation chunk (4.2, 5.3), so cross-build lists (`/v1/actions/{digest}/runs`, `/v1/shapes/{key}/runs`, `/v1/runs?node=`) serve `?tails=1` from chunks and never read a log blob; only `/failures` of a build still in the live recorder reads blobs.
- **A share of the read budget per caller.** **[F]** `READ_BUDGET_BYTES` (1 GiB) is one first-come-first-served budget for the whole route, with no per-caller share (`crates/kbf-server/src/http_blobs.rs:19-23`, `:58`). A page reads its logs one at a time (`invocations-api.md` 4.7), so one page holds at most 64 MiB, but nothing caps how many pages one caller has in flight, and open mode needs no credential. **[D]** (with Q18's listener): each caller (an authenticated principal, or the peer address in open mode) holds at most 25% of the budget and 4 concurrent reads; past either, `429` with `Retry-After`, never a wait that takes another caller's share (U1). Red test: one caller looping `/failures` and `/v1/blobs` reads does not make a second caller's `/failures` tails `busy`.
- **Live updates.** `GET /v1/invocations/{id}/events` is fed in process by the recorder on the single frontend (phase U1). `GET /v1/events/stream` carries state rows (nodes, leases, queue) from the state store's change feed (C5), after P1 (phase U5). Both are server-sent events resuming by revision (`Last-Event-ID`); a poller reading by revision gets the same rows. Subscribers are capped per caller (default 4) and in total (default 256), over that `503` with `Retry-After`; a stream closes after 5 minutes with no event. **[V]** With several frontends (P9) a build's calls land on several recorders, so the invocation stream then merges the frontends' chunks for that invocation (lagging by at most one 120 s flush) or needs a feed of its own.

## 7. Idle-host test scheduling (future)

Purpose: confirm flakes, refresh duration baselines and recheck tests not run lately, on capacity real builds are not using. It reruns recorded actions; it cannot test new code.

**Data.**

- Idle capacity per node: capacity minus booked CPUs and memory (`booked(worker)` is public today; capacity needs `Scheduler::snapshot()`, 4.4), as a 1-minute series (4.5).
- Idle time per node: how long the node has had no lease from a real QoS level.
- Candidates: test keys from 4.3 whose last executed digest's closure (Action, Command, input root) is still in storage; checked by FindMissing before submit.

**Controls.**

- **A band below real work.** **[F]** QoS levels are `interactive`, `ci`, `batch` (preemptible) and custom levels; every level at or below `batch` is preemptible (`crates/kbf-types/src/qos.rs:19-28`, `docs/design/scheduler.md:254-275`). **[F]** Today every action is submitted at `ci`, and preemption of `batch` is planned, not built (`scheduler.md:271-275`). An `idle` custom level below `batch`: never preempts, is always preempted, and is admitted only to a node with no queued real work for its partition and idle for a dwell (default 5 min).
- **No preemption, no band.** Until preemption is built, idle runs could delay real work by a whole run. Gate: the band ships only after preemption, or with candidates limited to p90 run time under 60 s, which bounds the delay.
- **Whose run it is.** An idle run is submitted under the original record's instance, by a farm principal whose authority is `Execute` only, on instances that opted in. Candidates come only from instances or shapes an operator marked rerunnable (a policy key, off by default), because a test with external effects (network, publishing) would run again. Results are recorded with `source: idle` under that instance only.
- **Budget**: CPU-hours a day, idle leases per node (default 1), and CPUs left free per node (default 2).
- **Selection** (ordered): digest-level possible flakes (`failure-classes.md` 6.3) to confirm; shape-level transition score above a threshold; test keys not run for 7 days; keys whose duration trend rose. Each idle run uses `skip_cache_lookup` and `do_not_cache`, so it never changes the action cache.
- **Results** go into history with `source: idle`; a `preempted` run is not an outcome. A pass after a fail is 6.3 case 1; an idle run that fails on a digest that passed before is case 2, the only way a fail after a pass is seen. That is what idle reruns add.
- **Off by default**, enabled by flag; `POST /v1/idle` (operator authority) changes budget and pauses; `GET /v1/idle` shows budget, spend, running idle leases, preemptions and results.

**Sizes [I].** Bounded by the budget: 100 CPU-hours a day of 30 s tests is 12,000 runs a day, about 14 MB of run records, about 3.5% of the daily volume.

**Prior art.** Borg's free band in reclaimed capacity, lowest priority, killed first; Kubernetes `preemptionPolicy: Never` for the never-preempts half.

## 8. Access control and secrets

**Today [F].**

- The invocation routes are off (`404 off`) unless the policy names `invocations.getAuthorizer` or `--invocations-open` is given (`crates/kbf-server/src/http_invocations.rs:7-12`, `:110-117`). A read asks that authorizer on every instance name the record's calls used, all of which must allow (`http_invocations.rs:136-170`, `pages.rs:474-487`).
- The blob route asks its own `blobs.getAuthorizer` on the caller-chosen `?instance=` parameter, and is off unless both `blobs.getAuthorizer` and `invocations.getAuthorizer` are present (`crates/kbf-server/src/http_blobs.rs:5-10`, `:98-104`; `crates/kbf-auth/src/policy.rs:29-35`). It then reads `cache.read_blob(&digest)` from a CAS that is not partitioned by instance (`http_blobs.rs:201`, `:211-215`). So **a caller allowed on any instance can read any blob whose digest it learns**: a digest is a read capability.
- **The action cache is shared across instances too.** `GetActionResult` authorizes the request's `instance_name` (`crates/kbf-front/src/action_cache.rs:62-68`), looks the result up by action digest alone (`:71`) and records the call under the caller's instance (`:72-77`). A caller allowed only on instance A who computes B's action digest (deterministic from public sources in an open-source repo) gets B's ActionResult, and a `hit` row would land in A's history. Per-instance history scoping therefore does not make the farm multi-tenant.
- **One plain-HTTP listener for every route.** Every HTTP route, the invocation pages, blobs, health, `/metrics` and `/v1/nodes`, is merged into the one operator router on `--api-listen` (`crates/kbf-server/src/serve.rs:315-326`). It is plain TCP, no TLS (`bind_api`, `serve.rs:190-198`), off unless the flag is given, and its help text says "Reads are open to whoever reaches it: bind it where only operators do" (`crates/kbf-server/src/config.rs:167-169`). A bearer token sent to it crosses in cleartext, and a `Secure` cookie is never sent to it at all.
- `GET /v1/nodes`, `/metrics` and `/readyz` are open reads, no authenticator, on the `--api-listen` listener only (`metrics.rs:6`, `api.rs:66-72`, `docs/api.md:221`). No `farm.get` authority exists (`policy.rs` has `invocations_get` and `blobs_get`).
- Authentication policies are `allow`, `deny`, `any` and `all` only (`crates/kbf-auth/src/policy.rs:271-276`); none reads a credential. Without a policy file the server uses `Policy::allow_all`, and every caller's metadata is empty (`crates/kbf-server/src/config.rs:519-523`, `invocations.md:170-172`); `--invocations-open` fills in `allow` for the invocation and blob reads (`config.rs:534-538`).
- **Not built: read tokens.** `invocations-api.md` 4.9 (`:207-220`) specifies a `bearerToken` authentication policy and a `read` role refused by REAPI, landing with the client tokens of issue 227. **[F]** Neither exists: `git grep -i -E 'RefuseReadRole|bearerToken' crates` finds nothing (the only `bearer_token` is the alert webhook's, `crates/kbf-alert/src/webhook.rs:27`). Until they land, an agent on another machine reads only from a server whose policy allows everyone who reaches the listener, or through an authenticating proxy, and every "token" below is a prerequisite, not a fact.

**Decided [D]** (section 10).

- **A TLS read listener [D] (Q18).** The read API and the pages are served on a listener separate from the loopback write gate, with TLS (`--read-listen` with `--read-tls-cert`, `--read-tls-key`), or behind the v2 LB's client TLS (`architecture-v2.md` 9, "Clients use TLS at the LB") with mTLS on the LB-to-frontend hop. It refuses to start without TLS unless `--read-listen-insecure` is given (for loopback or a trusted proxy), and the start line then warns. This is a prerequisite of read tokens and of the cookie option below (section 10 Q18). Phase U1; red test: `--read-listen` without TLS files and without `--read-listen-insecure` exits with a usage error, and a plain-HTTP request to a TLS read listener gets no page.
- **Tenancy [D] (Q14): (b) for v1.** Multi-tenant isolation is out of scope for v1: one farm per trust domain, every instance on a farm trusts every other, and the docs say so. (a), keying the AC by (instance, action digest) and then adding the digest-in-record check below, which only then isolates instances, is a design of its own if a multi-tenant farm is wanted: it changes the AC's key and storage sharding (`architecture-v2.md` 8), and a blob check over a shared AC is a check that cannot hold.
- **Instance scoping** (useful under either, as a view filter under (b) and a boundary under (a)). Every history record and index row carries `instance` (5.3); the test key is `(instance, shape, cfg)`. Every list or aggregate route (`/v1/invocations`, `/v1/actions/{digest}/runs`, `/v1/runs/{id}`, `/v1/shapes*`, `/v1/tests`, `/v1/grid`, `/v1/events`) returns only records and rows whose instance the caller's `invocations.getAuthorizer` allows, asked as the invocation routes ask today (once per distinct instance per request). An invocation spanning instances stays all-must-allow, as built.
- **Open mode.** `--invocations-open` (and a policy whose `invocations.getAuthorizer` is `allow`) opens every new GET route that `invocations.get` gates to anyone who reaches the listener: `/v1/invocations`, `/v1/invocations/{id}/*` reads, `/v1/runs/{id}`, `/v1/actions/{digest}/runs`, `/v1/commands/{digest}`, `/v1/trees/{digest}`, `/v1/shapes*`, `/v1/tests`, `/v1/grid`, `/v1/events`, and, as built, `/v1/blobs`, minus the raw Command gate below. It never enables a write or `commands.getRaw`.
- **`farm.get` [D] (Q11)**: a new `kbf-auth` authority for `/v1/nodes/{id}`, `/samples`, `/v1/queue`, `/v1/leases`, `/v1/storage/map`, `/v1/series`, `/v1/health`, `/v1/events/stream`. Under it, a lease or queue entry shows node ids, sizes, ages and counts; its invocation id, action digest and instance appear only if the caller's `invocations.get` allows that instance. The open `/v1/nodes`, `/metrics` and `/readyz` stay open: they name no build, and moving them would break scrapers.
- **Raw Command gate (under (a) and (b)).** **[F]** Today nothing keeps the raw Command off `/v1/blobs`: `--invocations-open` fills in `allow` for `blobs_get` as well as `invocations_get` (`config.rs:534-537`), and the blob route serves any digest under any caller-chosen `?instance=` (`http_blobs.rs:5-10`). Every run envelope publishes `command.digest` (6.3), so under open mode `GET /v1/blobs/{command digest}` would return a Command with `TOKEN=x` in its env. **[D] (Q19)**, independent of tenancy: `/v1/blobs` and `/v1/trees` refuse (`403`) a digest that the recorder or history holds as an Action or Command digest (the live recorder's rows, `invocation.proto:125`; the day index's digest and command sections within 30 days, 5.3, whose blooms make a miss cost no GET) unless the caller has a separate `commands.getRaw` authority. `--invocations-open` and an `allow` policy never grant `commands.getRaw`; read tokens do not get it by default. Remaining gap: a Command the farm never recorded (an id-less call before U3, or a digest past its 30 days) is still readable by its digest.
- **Digest-in-record check** (only with tenancy (a)). `/v1/blobs` and `/v1/trees` check the digest against the recorder and history (run records, outputs listings and pins; not hit records, whose result came from a shared AC under (b)) for an instance the caller is allowed on before serving.
- **Redaction is presentation, not a boundary.** **[D] (Q8).** Env values are never in a decoded command (decided in `invocations-api.md` flow (c)); operator redaction patterns apply to arguments, inline log tails and the shape catalog's program words (the key is computed before redaction, so keys stay stable). A program word holding a URL with userinfo is stored as scheme and host only: the shape normalizer keeps the argument after a bare program name as sent, so `curl https://user:token@host` would otherwise put the credential in `shape.program` (`crates/kbf-server/src/action_usage/shape.rs:43-59`, module docs on `program`). Full logs remain readable through `/v1/blobs`, and the raw Command through it with `commands.getRaw` only (the gate above, which `invocations-api.md:116-119` now names); the boundary is authority. Failure pins keep the redacted rendering, never the raw Command (4.2).
- **Purge** (O6) is a tombstone, because deleting one copy does not remove a blob in v2: reads fall back to replicas and previous-generation owners with read-repair (`architecture-v2.md` 8), handoff copies blobs (8), the cold store holds append-only segments (8, and P8 "cold store append-only"), daemon caches keep copies (`worker-cache.md`), AC entries name the digest, and history holds derived copies. `POST /v1/purge {digest}` on loopback with the write token, as cordon and drain are (`crates/kbf-server/src/api.rs:124-160`), does all of: (1) writes `purged/<digest>` in the state store, the one tombstone: every storage read, read-repair, handoff copy and closure check consults it first, answering NotFound and never repairing, and the UI reads the same row; it stays in the state store even when `--history-index` moves the `ui/` rows, as pins do (5.2); (2) deletes AC entries whose ActionResult references the digest; (3) tells daemons to evict it, carried in the map as the deny-list is (`architecture-v2.md` 9); (4) drops its pins; (5) rewrites each text-bearing history object holding text from the purged Command or log (chunks with command renderings, tails and reason text; windows; catalog deltas with `shape.program` words; test-case objects) under a new key (`<key>.p<n>`), swaps its index pointer by CAS and deletes the old object; failure-log copies (Q21) and reports are deleted outright; objects of digests and numbers only (day index, outcomes, rollups, series) are not touched, and the sweeper deletes by the day in the key, so a rewrite never extends retention; reads show the run `available: false, purged: true` from the `purged/<digest>` row; (6) records an event. Steps (1) to (6) on v1 cover the single store; replicas, read-repair and handoff exist only from P5 (R=2) and P6 (Rebalance) of `architecture-v2.md` 13, and the deny-list in the map from P3. Physical removal happens when compaction rewrites the segment holding the blob, within a bound the compaction design must state **[V]** (**[F]** no cold-store segment compaction exists today: `git grep -il compact crates` finds log compaction in `kbf-raft` and `kbf-store` snapshots and unrelated files, nothing over cold-store segments); until then the tombstone hides it. Red test (U5, single store): after a purge, `/v1/blobs/{digest}` answers `404` on the single frontend, the AC no longer returns a result naming the digest, and the run shows `purged`. Red test (U8, after P5/P6): killing the primary and reading through the replica or the previous-map owner still answers `404`, and no repair record is written.
- **Report writes.** `POST .../report` is off (`404 off`) unless the policy names an authenticator that yields a non-empty `public` principal (a per-caller authenticator: today none is built, 4.6). `--invocations-open` never enables it, and neither does `allow`. With one, it requires the owner match and, once roles exist, a non-read role, the 4.6 bounds and the per-owner quota. Red test (U4): with no policy file, `POST .../report` answers `404`.
- **Writes stay where they are**: cordon, drain, uncordon on loopback with a token; `POST /v1/idle` and `POST /v1/purge` the same.
- **UI pages.** Every page HTML-escapes every API string; a log, argv, JUnit case, target label, reason or file name is never rendered as markup. Every page answer sends `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; script-src 'self'; frame-ancestors 'none'` (no inline script) and `X-Content-Type-Options: nosniff`, as the blob route hardens itself today (`http_blobs.rs:14-18`). Red test (U6): a stderr of `<script>alert(1)</script>` renders as text.
- **How a human authenticates [D] (Q16): a reverse proxy for v1.** A browser cannot send `Authorization: Bearer` on page navigation. Either a reverse proxy injects the header (no farm change), or, once the TLS read listener exists (a `Secure` cookie is never sent over plain HTTP), a session cookie (`HttpOnly`, `Secure`, `SameSite=Strict`) is accepted on GET routes only, and every POST still requires the bearer header and refuses a request carrying an `Origin` header, as operator writes do (`api.rs:12-16`), so no cookie can make a POST. The proxy is v1; no cookie path until a POST is proven cookie-proof.
- **The UI is read-only** in v1; drain, cordon and purge stay CLI and API (PR #751's scope).
- History objects stay in the farm's own object store, under the prefix and credential of 5.2; nothing is sent anywhere else.

## 10. Decisions and open questions

**[D]** The owner accepted the recommendation of each of Q1 to Q19 on 2026-10-16, with two changes: the state store is an interface any backend may implement by passing the conformance suite (`architecture-v2.md` 4.1), and history is objects in the object store with a small metadata store of index rows (section 5). Q1, Q2, Q5, Q6 and Q19 below are recorded as amended by those changes. Q20 and Q21 come from the redesign and are open, each with a recommendation.

1. **History store home [D], amended.** History is immutable objects in the object store; the tables are `ui/` index rows on the `kbf-state` trait, in the state store's backend or a second instance of it (`--history-index`), rebuildable from the objects (5.2). No separate history database. `architecture-v2.md` section 1 (the frontend bullet, line 8) was amended in the same commit as this redesign: a frontend's durable state is the state store (scheduler and index rows) plus the object store (history).
2. **Durable invocation records [D], amended.** One durable record: invocation chunks as objects under `history/`, which keeps stage 2's chunks of `invocations.md` 3.5 without the Raft log, the root blob or CAS pins (5.2).
3. **Commit and target source [D].** The upload route first, the header if buck2 can send one from the environment [V].
4. **Test results inside outputs [D].** Client report only in v1; the files are linked either way.
5. **Failure pins [D], report half amended.** Failed runs' logs and result are pinned 30 days within a 20 GiB budget shared per instance, held by a pin set the storage evictor and collector consult (5.4), streams over 16 MiB unpinned, the Command kept as a redacted rendering in the chunk. Client reports are 7-day history objects under the per-owner quota, not pins (4.6). Q21 asks whether copies replace the failure pins.
6. **Retention [D], as classes.** 7 days for windows and reports; 30 days for run and hit records, tails, day indexes and pins; 45 days for daily objects; 400 days for invocation headers and summaries, outcomes, rollups, hourly series, events and the catalog (5.3).
7. **`/v1/flakes` [D].** One route: `/v1/shapes?kind=test&status=flaky`, with the proof digest; `failure-classes.md` 6.3 (and its stale "bounded table" text) is amended to say so.
