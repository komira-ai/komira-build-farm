# kbf-installer: contract

> **Retired in part.** The proxy's two-slot supervision of frontend children, its update API at
> `/v1/update/frontend` and the `kbf-installer update` client were removed: `kbf-installer
> proxy` serves a pool of frontends that run on their own (`[[proxy.frontend]]` tables) and
> refuses the `upstream` table. Passages below that describe them are history.

Status: design of record for the parallel PRs; on-prem only for now (section 13 lists what is deferred). Marks: **(built)** exists on `feature/pull-updates`; **(to build)** does not. Orders, the order spool, the fetch child, generation and the verification steps are agreed with `pull-updates.md` (#1024), which is their authority (section 12); settings, CLI, units and layout names are decided here, and #1021 (distribution), #966 and #1024 are edited to match (section 11).

## 1. Purpose
`kbf-installer` is THE package and the one root tool for setup and updates of kbf. It is the only writer of root-owned release files. It never updates itself; only the package manager does.
1. **kbf** is the runtime only: `kbf --mode=frontend|storage|daemon|storage-and-daemon|all-in-one` (or `mode = "..."` in `/etc/kbf/kbf.toml`; a flag overrides the file), with `--config` and `--check` as flags (`--instance` is accepted and ignored). There are no positional arguments and no `node` mode. The old subcommand forms stay as aliases until the test farm has moved, then are removed. kbf never installs, fetches or restarts anything. It writes an order record into the installer's `orders/` directory (section 4) and reports status. kbf.toml has no installer keys; the one update setting is `[daemon] update-dir` and `orders-dir` of a host whose daemon takes orders (`daemon`, `storage-and-daemon`), which `setup` writes from the layout and `migrate` adds to an adopted host (without them the node updates by hand and ignores orders; the in-process daemon of `all-in-one` refuses `--update-dir`, so that mode has neither). Enrollment runs inside the start of the `storage`, `daemon` and `storage-and-daemon` modes; the enrollment token limits which roles a host may hold. There is no `kbf enroll`, `kbf ca` or `kbf token` command: the frontend creates its CA on first start into an empty `--ca-dir`, and tokens are operator-API routes.
2. **kbf-installer** pulls the kbf release itself (an unprivileged fetch child from the one configured source; nothing is root-owned before it verifies), installs, verifies, activates, confirms and reverts releases. It takes its orders from the kbf-owned `orders/` directory, keeps its state under the root-owned `/var/lib/kbf-installer`, and reads its settings from `/etc/kbf/installer.toml`.
3. **The package** ships `kbf-installer`, the unit files (disabled) and the trust files. It ships no kbf runtime release; `record-release` records the first one. It has no package `Depends:` on Envoy, and nothing installs, checks, renders or reloads Envoy (section 5.1, retired).

Updates are triggered externally (section 6): nothing in kbf or in the installer decides to update. Not goals: self-update, cloud update providers, fetching or pinning Envoy, an installer network listener, root logic in kbf.

## 2. CLI
One binary (**to build**; today a library plus `kbf-helper`). Mutating verbs are a dry run without `--apply` (**built**). Flags: `--json`, `--apply`; `--root DIR` exists only in builds with the `test-sandbox` feature. Exit codes: 0 ok; 1 failed; 2 usage or missing prerequisite; 3 refused (verification, policy); 4 busy; 5 needs operator. Every verb but `status` and `check` needs root.

| Verb | What it does |
|---|---|
| `setup` | First install. `--mode` (the kbf mode this host runs), `--min-generation`, `--no-start`. `--release-source`, `--release-url`, `--release-ca`, `--frontend-worker-url`, `--frontend-ca`, `--frontend-ca-sha256` and `--commit` are retired: taken and ignored for one release, with one warning naming the ones given. `--token-file` (the enrollment token; node modes only), `--frontend-url` (node modes; goes into `kbf.toml`), `--database` (frontend and all-in-one, optional: the Postgres URL, written to `installer.toml` and to `kbf.toml` as `state-store`, whose schema `setup` creates; left out, it is the local default and `setup` makes the role and database, see section 14). Installs no release (`kbf` comes from its own package, and the mode unit is started when `/usr/bin/kbf` or a release is installed; a release placed by hand is made current with `record-release`), writes `installer.toml` (the only writer), **writes `kbf.toml`** (mode and frontend URL) **and places the token** from `--token-file` (0600 root:kbf), creates users and directories. (It once checked the installed Envoy against a tested range first; that check is retired, section 5.1.) `setup --mode=frontend`, run as root, also creates the **first operator token** once, writes it to `/etc/kbf/api-token` (0600, owned by the service user) and prints that file's path, never the secret; it creates none once any operator token exists (the only token path that does not go through the operator API). Idempotent. |
| `status` | Current, previous, staged, pending confirm, last refusal. `--json` equals `status.json` (section 4). |
| `run` | Run by `kbf-installer.service`, no listening socket. `--unit` or `--launchd-label` names the service it restarts after a swap; without either (the packaged unit), the unit of the `mode` in `kbf.toml`. At start, once, under the lock: remove the `work/<commit>.partial` and `work/<commit>.check` a killed stage left (nothing else in `work/`; a failure is logged, and the start goes on), then make the links agree with the state. Each pass: finish an owed restart, revert an expired swap, act once on each record in `orders/` in (epoch, id) order, write status. No release polling. |
| `update --commit SHA --frontend` | Removed (the verb no longer exists; see section 6). It was the frontend host's own update, run by whatever external trigger the operator used. Needs no root and is refused through `sudo`: it is a TLS client of the proxy's update API (`--api`, `--token-file`, `--api-ca` are required or defaulted from the caller) that waits for the update to end. It writes no order and takes no installer lock; the API writes the `frontend_update` order. `--source fetch` (the default) or `staged` says where the release comes from: the source the installer is configured with, or the release the host's package carries; the request names it only for `staged`, and a staged update takes no `--nodes` yet. Exit 3 when the host refuses the source; exit 4 when an update is open or an old child is draining. |
| `confirm`/`revert ID` | Operator override of a pending swap, naming the activation id; inline under the lock. Exit 5 if none pending. |
| `rollback` | `current` to `previous`, no window. Operator only; the only verb allowed below the release floor. On a host whose `release_source` is `bundled` it is refused (exit 3, dry run too, before anything is written) when the previous release's `kbf --version --json` does not declare `relay >= 1`, asked of its own binary as the unprivileged user; one that cannot be asked counts as not relaying. A bundled host fetches nothing, so a new kbf reaches it only as a staged order, and a kbf that cannot relay one would leave no way to update. A url or frontend host, or one whose `installer.toml` cannot be read, is not held to it. |
| `record-release` | Make a release placed by hand the first one: checks `releases/<sha>`, writes `VERIFIED`, makes it `current`. The operator vouches; nothing is fetched or attested (the frontend proxy starts only a `VERIFIED` release). Operator only. |
| `gc` | Keeps current, previous, one more. State-aware (S22). |
| `boot-check` | Counts starts of a release on trial; reverts when the budget is spent (**built** logic). Also saves and restores the node's metadata log (see "The metadata log across a rollback"). |
| `quiesce` | For maintainer scripts: takes the lock, exit 5 if a swap is pending (S25). |
| `check` | Validates installer config, trust files, path chain. Lists every problem. (It once also tested the installed Envoy against a range; retired, section 5.1.) |

`stage`, `activate`, `fetch-child` are internal.

## 3. Files, ownership, one source per setting
Three roots, never nested: kbf's own state `/var/lib/kbf` (user `kbf`, systemd StateDirectory, untouched by the installer); the installer tree `/var/lib/kbf-installer` (root:root 0755, not kbf's StateDirectory; everything the root side reads as authority lives here); package files. Only `orders/` in the installer tree is writable by `kbf`.

Package-owned (root:root, no group/other write, changed by package upgrade only):
- `/usr/bin/kbf-installer`, `/usr/lib/systemd/system/kbf-*.service` and `kbf-*.timer`: of the `kbf-installer` package, the units of the installer and the proxy (`kbf-installer.service`, `kbf-proxy.service`, `kbf-proxy.socket`) and `kbf.slice`.
- **The `kbf` package** (a second package, `docs/artifacts.md`): `/usr/bin/kbf` (0755) and the unit of every mode (`kbf-all-in-one.service`, `kbf-daemon.service`, `kbf-frontend.service`, `kbf-storage-and-daemon.service`, `kbf-storage.service`). It depends on no package (each mode unit runs `kbf boot-check`, the file the package carries) and, as a deb, replaces `kbf-installer` (the units were that package's files), and neither package has a maintainer script. A host set up from the packages has no `releases/` tree and no `state.json`: its mode units run `/usr/bin/kbf`, and installing a newer `kbf` package is the update. The package restarts nothing, so the operator restarts the mode unit (a stop drains). `kbf-proxy.service` is not changed by the package split.
- `/usr/share/kbf-installer/trust/`: pinned `gh`, `trusted_root.jsonl` (with `valid_until`), `installer.conf`. Its parser (`settings.rs`) reads three keys today: `SOURCE_REFS` (space separated; default `refs/heads/main`), `RUN_AS_UID` and `RUN_AS_GID`. The signer workflow, OIDC issuer and repo are constants of `attest.rs`; the `deny` commit list and the tested Envoy version range of section 5.1 are not read by anything yet (the range is P9). Replaces `/usr/local/libexec/kbf-deploy`. Allowed source refs live **only** here; `installer.toml` may narrow them, never widen (set intersection, applied at each fetch: the refs both name, in this file's order, and a file that names none of the allowed refs refuses the fetch). **Decision D4 (open, with the lead):** the default names `refs/heads/main`, but the farm's releases are attested for `refs/heads/feature/arch-v2` until arch-v2 merges to main, so a host that installs them needs `SOURCE_REFS=refs/heads/feature/arch-v2` in its `installer.conf` (a root-written trust file) or every release is refused (`attestation`).

Installer-owned (root:root):
- `/var/lib/kbf-installer/releases/<sha>/`: `kbf` (the one component on every platform, macOS included), `units/`, and a `VERIFIED` marker written into the directory before it is renamed into place. Files 0755/0644; no setuid, setgid or file capabilities.
- `/var/lib/kbf-installer/releases/current`, `releases/previous`: relative links to `<sha>`.
- `/var/lib/kbf-installer/state.json` (0600, schema 2) and `state.json.bak`; it supersedes the schema 1 `helper.json` of #1024. `status.json` (0644, section 4). `seq_floor` beside `state.json` (0600, one decimal and a line end): the highest `seq` a staged order may not use, so a seed must be strictly above it. It starts at the `seq` of the release that runs (`kbf --version --json`, asked once per release as the unprivileged user) on a host that has none, and `setup` writes the package's release's `seq` for the first release it installs; it rises when a swap is confirmed (the node's confirm, the frontend's flip; the operator's own confirm is caught up at the next pass) and never at a stage or while a swap is on trial, so a trial that is reverted does not burn the seed; a rollback lowers nothing, so the release rolled back from stays unorderable until a newer package arrives. A release that declares no `seq` raises nothing, and a host with no floor admits no seed. `work/<sha>.partial/` (0755, extraction; `dl/` inside it 0700 holds the tarball), swept at every start. `orders/` (`kbf:kbf` 0700). Lock `/run/kbf-installer/lock`.
- Layout constants live in `layout.rs`, one place. macOS: root-owned `/usr/local/kbf-installer` tree (not a user-owned Homebrew prefix), `/var/db/kbf-installer` for state.

`state.json` schema 2 (types fixed by the golden fixture, section 9 P1; `deny_unknown_fields`): `schema`, `current`, `previous` (confirmed releases only), `staged`, `pending_confirm {activation "<epoch>-<order_id>", commit, previous, deadline_wall, deadline_mono_s, starts_left}`, `floor {epoch, order_id, generation}`, `serving_instance` (frontend), `last_acked_order_id`, `unacked` (copy of the order being acted on, with root's first-seen time of each record in `orders/`). `floor` replaces the built, unused `order_floor`. Schema 1 to 2 migration (including the string activation id) belongs to P3.

Config:
- On macOS the configuration directory is `/usr/local/etc/kbf`, not `/etc/kbf`: `kbf.toml`, `installer.toml`, `enroll.token` and `api-token` below are there (`layout.rs`), and it is the `installer.toml` there that the launchd job's `KeepAlive` waits for.
- `/etc/kbf/kbf.toml`: kbf's runtime config, root:kbf 0640 (#966). The installer reads only its existence and its `mode` key (to know whether this is a frontend host). On Linux `setup` owns `[daemon] update-dir` and `orders-dir` in a node's file (the state directory and its `orders/`, `Layout::update_dir` and `Layout::orders_dir`): a file that holds other settings and lacks them, or names another directory, is refused by key name. On a Mac (any Mac, kit-adopted or not) `kbf-mac-provision` is the one writer of the daemon's `kbf.toml`: `setup` and `migrate` check and never write it. `update-dir` must be there and be the layout's; `orders-dir` must be absent (the node derives `<update-dir>/orders`) or the layout's; a missing or different key is refused (exit 5), naming the key and saying `kbf-mac-provision` renders it, with no path.
- `/etc/kbf/installer.toml` (root:root 0644, TOML, unknown keys refused by the readers that decide where a release comes from; the `proxy` verb checks only `confirm_window_s`, `confirm_window_max_s`, `fetch_timeout_s` and `[proxy]` through the tolerant reader, ignoring every other key (`database` it reads separately, leniently), so a package downgrade does not stop it): `release_source` (`url`|`frontend`|`bundled`: `bundled` fetches nothing and excludes every key below that names where to fetch from), `release_url`, `release_ca` (`url` only: a PEM file of the roots to trust instead of the system's), `frontend_url`, `frontend_ca`, `frontend_ca_sha256` (`frontend` only, all three or none: the frontend's worker listener, a copy of its CA and that copy's sha256, which `setup` wrote; not read by a fetch yet), `source_refs` (narrowing only), `confirm_window_s` (default 900, bounds 120-1800), `confirm_window_max_s`, `min_generation`, `min_protocol` (operator floors), `fetch_timeout_s` (900, bounds 60-3600), `max_component_bytes` (512 MiB, at most 1 GiB), `min_activation_interval_s` (60), `database` (frontend and all-in-one hosts: the state database's `postgres://` URL, no password; section 14), and for the `frontend` source `node_cert`, `node_key` (paths of the certificate and key that enrollment, inside the start of the node modes, writes under kbf's state; the installer opens them `O_NOFOLLOW` at each fetch and lends them to the child, section 5). A `storage-and-daemon` host holds two role pairs: `setup` points `node_cert` and `node_key` at the daemon pair if present, else the storage pair. An `all-in-one` host does not enroll (no remote roles), so it has no pair and uses the `url` source. `[proxy]` (frontend and all-in-one hosts; the proxy's own table, closed like the file) holds `listen`, the public `host:port`: `setup` turns it into the drop-in `/etc/systemd/system/kbf-proxy.socket.d/listen.conf` (`ListenStream=` empty, then the address; root 0644, atomic; removed when the key is gone) and tells the operator a `daemon-reload` and a socket restart are due, because it never restarts the public port itself. A host's first release therefore comes from the `url` source or a release `setup` was given; it can switch to the `frontend` source once enrolled. Source is read only from this file, never from an order, offer, environment or flag outside `setup` (an order's own `source` word, `fetch` or `staged`, only picks between that configured source and the release the package carries; it names no place, and `fetch` on a `bundled` host is denied). This supersedes `[update]` in kbf.toml of #1024.

Users: `kbf` (runtime). `kbf-server` (the frontend and storage units; the user builds run as must not read the state store, the operator token or the keys). `kbf-signer` (frontend and all-in-one hosts only): owns the key that signs certificates and grants, so the frontend process cannot read it; the signer binary ships as a release component and the frontend reaches it over a local socket, with `kbf-signer.service` (section 7). Until that is built, the frontend uses the in-process file signer (#966). `kbf-fetch` (`_kbf-fetch` on macOS): dedicated, no home, `nologin`, no groups, owns no file; it runs the download and the `--version --json` probe, never anything with credentials. **`kbf-signer-clients`** is the group the signer shares its socket and its root with: the sysusers file makes it with `kbf-signer` (a process can only give a file to a group it belongs to) and `kbf-server` (the frontend connects as a member) as its members, and `kbf-signer --client-group kbf-signer-clients` makes the socket mode `0660` in a directory of mode `0750` and `ca.pem` mode `0640`, all of that group; `ca.key` stays `0600` and the signer's. The signer still serves only `--frontend-uid` and the group's members. Without the flag the socket is `0600` in a `0700` directory. There is no `kbf-verify` user (the package's sysusers file creates `kbf`, `kbf-server`, `kbf-fetch` and `kbf-signer`; it is one file for every host type, so `kbf-signer` exists on a node-only host too).

## 4. Order handover
Channel decides authority, not a body field. There is no order socket, no control socket and no installer listener.
- **Wire orders** reach the installer only as files in `/var/lib/kbf-installer/orders/` (`kbf:kbf` 0700 under the root 0755 tree, so `kbf` traverses to it). `kbf-update` writes one record per order, to a temporary name starting with `.` and renames it into place; the installer ignores dot names. The installer opens `orders/` with `openat` relative to a descriptor it holds and `O_NOFOLLOW`, takes an entry only if `fstat` says a regular file with one link, reads it **once into memory** (at most 1 MiB) and parses from that copy, never re-reading a path; it then removes the entry by name through the same descriptor. At most 64 records are held. A record is expired and removed when older than the confirm-window maximum (1800 s) **measured from root's first-seen time** (kept in memory and in `state.json`), never the file's mtime, so a stuck or hostile writer cannot grow the directory or replay a stale order after a restart. A larger, unparsable, symlinked or non-regular entry is refused and removed. A record is a locator and a set of claims, not trust.
- **Operator orders** (`confirm`, `revert`, `rollback`) are CLI runs as root (section 2); `kbf` cannot run them. (`update --frontend` and the proxy's update API, which wrote the `frontend_update` record below, were removed.) A `frontend_update` record is accepted only on a host whose `kbf.toml` mode is `frontend` or `all-in-one`, and only from `orders/`; it is subject to the same ordering, floors and refusals as `activate`.
- **Record**: `{ "order_id": u64, "epoch": u64, "generation": u64, "verb": "activate"|"confirm"|"revert"|"frontend_update", "commit": "<40 hex>", "window_s": u32 }`; for `activate` also the components (from the offer the node holds) for the host's own platform (`name`, `sha256`, `size`, `attestation`, each at most 256 KiB of bundle) and the **expected facts** `platform`, `protocol`, `min_protocol`, `state_schema`, `profile` from the frontend's preflight. Unknown and duplicate keys refused. Nothing in a record is a path, URL, command or unit; unit names come from a code table (S2). The activation id is `<epoch>-<order_id>`. A node holding no offer for the commit writes no record and reports `refused` ("no offer for this commit"). A `frontend_update` record carries none of the components or expected facts (the root half fetches by commit and probes; see section 6).
- **Ordering**: (epoch, order_id), each once (**built**): older epoch and replays dropped, a jump above 1000 beyond the floor refused, a parse failure never advances the floor. **Also** (epoch, generation) lexicographically: within an epoch the generation must be at or above the highest acted on and at most 1000 above it per order; generation 0 refuses `activate`. A rollback is the old release ordered again with a higher generation. This stops a replay, not a forgery by a compromised `kbf`; against that the defence is the operator floor (`min_generation`, `min_protocol` in `installer.toml`), and the intended end state, a frontend-signed grant verified before any fetch, is not designed here.
- **Refused before any fetch** (reason in `status.json`): replay or older, commit not 40 lowercase hex, component set not exactly what the platform needs, size over `max_component_bytes`, expected facts missing (fail closed), a pending trial, below the floor, or a live lease. The installer observes leases itself (Linux: the cgroup of the action unit; macOS, daemon running as its own account: the daemon's keeper processes and its lease directories); the record's claim is never used. On Linux `run` reads the lease cgroups of the unit it restarts, which must be a unit of a `kbf` mode (the units `setup` enables, and the other instances and the plain form of the same unit): a unit of no mode, or a unit whose cgroup does not exist (a stopped or failed unit has none: start it, then order again), cannot tell and the activation is refused. When the unit `run` restarts is the frontend mode's (`kbf-frontend@<instance>.service` or the plain `kbf-frontend.service`), an `activate` is refused as `denied` before any fetch, since a frontend holds no leases and moves by `frontend_update`; every other mode's unit, `all-in-one` included, takes it. On macOS the lease count is the larger of the `kbf-keeper` processes (`pgrep -f`; processes are read first) and the `lease-*` entries of `<data-dir>/leases` (read last; `lease-survey` and `lease-warm-up[-<n>]` are the daemon's own and do not count, every other `lease-` name does), with `data-dir` from the root-trusted `kbf.toml`. It cannot tell, and the activation is refused, when the host's `kbf.toml` is untrusted or is not a native daemon's (a pool key included), when the running daemon was not started by launchd as exactly `kbf --mode=daemon --config <kbf.toml>` or started before `kbf.toml` last changed, when `/usr/bin/sandbox-exec` is not a file, when the check does not run as root, when `leases/` cannot be listed, and whenever `pgrep` or `ps` fails, times out, is cut at the 64 KiB capture or prints what is not a list of pids (only `pgrep` exit 1 means none). One judgment lets an activation through: lease directories remain, no keeper exists and no kbf daemon runs; the pass logs each directory, which the daemon's start-up sweep removes. Pool mode (`pool-users`) is not read yet and is refused. A `frontend_update` is not held by leases: it moves no node link, and the swap and the proxy own the frontend's streams. The expiry revert and the restart after a crash are not held by leases either: they finish or undo a swap already made.
- **Unacknowledged orders**: the record is removed after it is read, but the order is acknowledged only after the flip, so the installer keeps its own copy in `state.json` and reruns it from the start (nothing was flipped, so repeating is safe) unless it has expired.
- **`window_s`** is an input, clamped to `[120, confirm_window_max_s]`; on Linux the window starts at the first start (`boot-check`), so `window_s` is advisory there; on macOS it arms at activation.
- **Status**: `/var/lib/kbf-installer/status.json` (root-owned 0644, atomic rename; in the persistent tree, so it survives reboot), schema 2: **built** fields `installed_commit`, `previous_commit`, `staged_commit`, `state`, `refusal` (the last refusal as text, usually leading `<word>: <message>` with the word of the set below; some are plain sentences), `acked_order_id`, `refused_order_id` (the id of the proxy's order that `refusal` answers, left out when it answers none, as for a node's order; the helper holds it from pass to pass and never writes it to `helper.json`, which older builds refuse to read with a key they do not know), `staged{protocol, min_protocol, state_schema, profile}`, `envoy{}` (nothing set yet), `release_source`, `available{commit, seq}` and, when a link names a release without a `VERIFIED` marker, `unverified`; **not built**: the probe's reported facts and the days left on the trust root. The golden `crates/kbf-installer/testdata/golden/status.json` is the writer's bytes, and the strict reader `status_v2.rs`, the node's reader (`kbf-update`) and the proxy's are tested against them, so a key added to the writer moves the file in the same change. `release_source` is the word `installer.toml` holds (`url`, `frontend`, `bundled`), left out when the file cannot be read: a host that fetches nothing is told so to the frontend, which would otherwise order it a fetch the installer can only refuse. `available` is the seed the host's package carries (the release of its own commit, under `seed/<commit12>/`): told only when the run loop has found it whole, which is the package's files root's and this build's, the tarball the size and digest the manifest names, the three trust files the ones the manifest was made beside (a package half way through an upgrade is not whole), and the attestation valid offline for the manifest's commit; and only when its `seq` is above the floor (below), by the rule an order meets. The look is made at the end of each pass, after the status of the pass's orders has been written, and a package found whole is read in full once per manifest (a file changed under the same manifest is found when an order is taken on it, which checks everything again); a look that fails is not made again for a minute. It installs, stages and moves nothing (its one scratch directory, `work/<commit>.look`, is its own and gone when it returns), and why a seed is not told is said in the log, once. The floor is kept at the `seq` of the release that runs while no swap is on trial, and a staged order catches it up before it is judged. `state` words: `idle`, `fetching`, `staged`, `activated_unconfirmed`, `confirmed`, `reverted`, `refused`, each 1:1 with `UpdateStatus.State`. `helper_present` means installer present. `kbf-installer.service` starts before the runtime units (`Before=`); `/run/kbf-installer` (tmpfiles.d) holds only the lock.
- A swap pending refuses `activate` (`pending`, exit 4): one confirm window at a time, and `previous` is only ever a confirmed release. A confirm is accepted only if it names the pending activation, the unit is active, `/proc/<MainPID>/exe` is in `releases/<current>`, and the first boot-check has run.
- **macOS**: `kbf` runs as root there, so a compromise of `kbf` is a compromise of root; the separation of this section holds on Linux only. The fetch child and the probe still run unprivileged.

## 5. Fetch and verify
**Release source** (from `installer.toml`, never from an order; an order's `source` word only picks this or the package's release): `frontend` (default; `ReleaseService.Fetch` by sha256 over mutual TLS, server authenticated by the pinned CA and the frontend name checked against the certificate SAN) or `url` (an HTTPS file server with the store layout `files/<sha256>`; system roots are the transport anchor only, bytes are trusted by verification, not TLS). Reading `installer.toml` refuses non-https, user information, query or fragment. **The child follows no redirect at all**; any 3xx is a failed fetch. No other source is contacted; a compromised frontend can only serve bytes the verification refuses. **Built:** `run` makes its fetcher anew for each fetch, from `installer.toml` as it is at that moment (so a second `setup` takes effect in a running `run` with no restart). `setup` makes none: it fetches nothing. The file is held to the trust files' rule: a plain file of root's that group and others cannot write, in directories likewise, else the fetch is refused. The `url` source works, with the system's roots. The `frontend` source is refused: `installer.toml` has no key yet for the frontend's address or the pinned CA. The version numbers a release may declare are capped by constants of the installer (`stage::supported`: protocol 1, min_protocol 1, and the newest state schema it embeds; **decision D3, open with the lead**, since they decide which releases a host can ever accept); a test in `kbf-cli` fails when `kbf --version --json` declares more. The lease source of `run`'s fetcher is the helper's: `leases::for_restart` of the restarted unit (a cgroup read for a mode's unit, one that cannot tell for any other unit, and for launchd the Mac source above), made anew for each fetch. An activation is refused at the pipeline unless the lease source says none is live; a frontend update (a first release or `frontend_update`) skips the lease step.
**Assets**: tarballs `<name>-<40hex>-<platform>.tar.gz` (**built**, platforms `linux-x86_64`, `linux-arm64`, `darwin-arm64`), each attested by the release workflow as its own subject. The attestation bundle travels in the order record, from the offer the frontend published; it is self-authenticating, so the frontend is a courier, not a trust anchor. Hosts never fetch `SHA256SUMS` (advisory only) and never use `gh attestation download`. The release carries no manifest of its own: the facts it declares come from `kbf --version --json` and are checked against the record (step 5). What a commit holds is another matter: the source describes a release on request (next paragraph).

**Describing a release** (**built**: the server's `Describe` and `GET /v1/releases/{commit}`, and the installer's `fetch::describe_release`, which `helper::fetcher_real::RealFetcher` calls for a `frontend_update`). An `activate` record carries its components, taken from the offer the node holds. A `frontend_update` record is a locator, a commit and nothing else, so the root half asks the release source what the commit holds, then fetches and verifies each component as for an offer. **The root half never parses the source's bytes**: the question goes through the same confined fetch child (`fetch-child --describe <commit> --platform <host's platform>`), which decodes the protobuf or the JSON and writes a small fixed form on its standard output (`description 1 <commit>`, then one `component <name> <platform> <tarball> <sha256> <size> <bundle_sha256> <bundle_size>` line per entry; or one `refused <text>` line, written for `NOT_FOUND`, `FAILED_PRECONDITION`, a `404` or `409` and a file of another `schema`); the parent reads that form with a strict reader and holds every field of the host's platform to its shape again, since it is the word of a child that read a stranger's bytes. Entries of other platforms are not read: the `frontend` source is asked for the one platform, and the child skips the others in the `url` file (which lists every complete one) unread, so a fault in an entry the host does not take is no fault of its release. The host's platform must have each component `ReleasePlatform::components` lists, once and no other. The `frontend` source answers `ReleaseService.Describe(commit, platform)` on the worker listener, to the same callers as `Fetch` (the daemon role under mutual TLS); the `url` source serves `<base>/releases/<commit>.json`, the same fields as JSON with a `schema` of 1 (`docs/api.md`, "`ReleaseService.Describe` and `GET /v1/releases/{commit}`"; on a frontend, `GET /v1/releases/{commit}` is that file). For each component the description gives the tarball (`name`, `platform`, the file name, `sha256`, `size`) and the bundle that attests it (`bundle_sha256`, `bundle_size`), both of them fetched by digest like any component (`Fetch`, or `files/<digest>` on a `url` source), the bundle within 256 KiB. **A description is a claim, as an offer is**: the stage takes from it only which digests to fetch and the sizes that bound them, and re-derives everything that matters (steps 1 to 5: count, digest, the bundle's subject digest, the attestation per tarball, shape, the binary's own report). It refuses (`fetch`) a description it cannot read strictly: an unknown `schema`, a commit other than the order's, a component of the host's platform that the platform does not use (or one it needs that is missing or listed twice, or a file name other than `<name>-<commit>-<platform>.tar.gz`), a digest that is not 64 lowercase hex, a bundle over 256 KiB or a tarball over `max_component_bytes`, or a description over 16 KiB. A `FAILED_PRECONDITION` from `Describe` (the release is not complete for the host's platform; the message names what is missing) and a `404` or `409` for the JSON are a refused fetch with that reason, not a retry.

**Fetch child** (`kbf-installer fetch-child`, **to build**; the same binary, one child per component, per attestation bundle and per description, also used by `setup`): the root parent sets `setgroups(0)`, `setgid`, `setuid` to `kbf-fetch` (ids read back), `no_new_privs`, `chdir /`, an empty environment, closes every descriptor but 0 (`/dev/null`), 1 (byte pipe), 2 (log pipe) and 4 (lent identity), `RLIMIT_FSIZE` 0 (it cannot create a file), `RLIMIT_CORE` 0, `RLIMIT_NOFILE` 16, `RLIMIT_AS` 1 GiB, small `RLIMIT_NPROC`; Linux `PR_SET_PDEATHSIG`; macOS kills the process group when the pipe closes. A descendant that leaves the group (`setsid`) survives that kill, and the child is dumpable again after its `exec`, so a survivor could read the identity lent to the next child through `/proc`: after the switch of user, each new child first kills every other process of the fetch user (the account owns nothing and runs nothing else), and on Linux `fetch-child` makes itself non-dumpable as its first act. The parent refuses to start a child that would run as root (uid or gid 0), named or inherited, whoever built the request. Seccomp and `sandbox_init` are later hardening, not required. **Bytes pass through the pipe**: the child writes the tarball to stdout; the parent hashes while reading and writes a file it created in root-owned `work/<sha>.partial/dl/`, so the child has no object to swap or link. Stderr is read up to 4 KiB and never parsed, the rest drained; the parent uses `poll` and non-blocking reads. Caps: at most `size` bytes (one more kills the child, fewer is a failed fetch), connect 30 s, 60 s without a byte, `fetch_timeout_s` per component, no ranges or resume. Free space under the installer tree must cover the tarball, its extraction (1 GiB or ten times the declared size if smaller) and the release it replaces, computed before anything is opened. A short read, timeout or unreachable source is `refused` with that reason and is not retried; the frontend holds the run and a person re-issues it.
**Identity**: for the `frontend` source the parent lends the node certificate and key named in `installer.toml` (on a two-role host the daemon pair if present, else the storage pair; `ReleaseService.Fetch` admits any enrolled role) over descriptor 4 (Linux anonymous memory file; macOS socketpair; never disk). The parent opens the files by an absolute path with no link followed in any component (Linux `openat2`; where that is missing or off Linux, the last component only), and they must be regular files with one hard link. **A compromised child can steal the node key**: an accepted v1 residual (seven-day certificate). The follow-up is a fetch-scoped client certificate (a distinct extended key usage accepted only for `Fetch`), which replaces P15's proxy idea.

**Every root step is bounded**: wall-clock limit, process group killed on expiry, output read up to 4 KiB and parsed strictly; `gh` runs with an empty environment and empty `HOME`. Limits: 120 s `gh`, 120 s extraction, 10 s probe.

**Verification order**, by the root parent, on files it opened itself (`O_NOFOLLOW`, `fstat` regular and owned); nothing is unpacked or run before step 4:
0. Trust files and every path component of installer, `gh`, trust dir are root-owned, not links, not group/other writable (`openat2` walk). Trust `valid_until` not passed (exit 5), with days left in `status.json`.
1. **Count**: exactly `size` bytes arrived, within `max_component_bytes`.
2. **Digest**: the SHA-256 computed while reading equals the record's `sha256` **and** the attestation bundle's subject digest (the record's digest is only a locator).
3. **Attestation**, offline: pinned `gh` and `trusted_root.jsonl`, `--repo`, `--signer-workflow`, `--cert-oidc-issuer`, `--source-ref` (allowed refs), `--predicate-type`, `--deny-self-hosted-runners` unless decision 6 says otherwise, and `--source-digest` equal to the order commit (**built** `attest.rs` flags). Failure ends the order; nothing from the child is read further.
4. **Shape**: gzip and tar with exactly one regular file named `<name>` (no link, device, directory, absolute path or `..`), at most 1 GiB, extracted by the parent into `work/<sha>.partial/` as root, mode 0755. Binary kind and CPU checked; macOS quarantine refused and `codesign --verify --strict`.
5. **The binary names itself before the flip**: `<name> --version --json` run as `kbf-fetch` (empty environment, no credentials, no network that is enforced in v1) reports the order commit (12 hex prefix) and `protocol`, `min_protocol`, `state_schema`, `profile`, `platform` that must equal the record's expected facts, satisfy the operator floor, and be supported by this installer (else `installer_too_old`). Mismatch refuses before anything is renamed.
6. **Install**: write `VERIFIED` into the directory, rename to `releases/<sha>`, fsync the parent. The pipeline does not write `state.json`: the order that asked for the release records it once its own checks pass (`staged` for a `frontend_update`, `current` for an `activate` or setup's first release), so an order refused after the fetch leaves `staged` as it was, and a release made `current` is no longer `staged`. A `releases/<sha>` without `VERIFIED` and not referenced by `current`, `previous` or `pending_confirm` is removed; a referenced one stays and is flagged "unverified: rollback to it refused". "Already installed" means `VERIFIED` exists, never skips verification of a new fetch, and a rollback to it skips steps 1-4 but reruns 5. Directories made by the test-farm switch never carry the marker.

### 5.1 Envoy is an installed prerequisite (retired)
This section is history: nothing in the installer installs, checks, renders or reloads Envoy any more, and `setup` and `check` test no range. The `envoy` field and the `envoy_range` word survive only in `status.json`'s schema. The frontend's update path needs an Envoy in front of it (section 6). Envoy is not part of a kbf release and the installer never fetches, pins, installs or upgrades it. It is **not** a package `Depends:`: one `.deb` serves every host and a dependency cannot apply per host, and there is no separate frontend package. Host preparation installs it, on frontend and all-in-one hosts only. The range is the one the farm has tested, kept in the package-owned `installer.conf`; `setup --mode=frontend|all-in-one` and `check` refuse a host whose Envoy is missing or outside it, with one clear line and the fix. The installer renders kbf's Envoy configuration for the frontend's ports and instances and asks the installed Envoy to reload it; the Envoy service itself is its own package's. Changing Envoy across versions is not designed here (section 13).

**Refusals** (exit 3, stable `refusal` word): `trust_chain`, `hash`, `attestation`, `commit_or_ref`, `facts`, `installer_too_old`, `platform`, `size`, `disk`, `fetch`, `replay`, `generation`, `floor`, `pending`, `lease`, `denied`, `envoy_range` and `frontend_busy` (frontend update only: a second `frontend_update` order while one is in flight). Lock contention is exit 4, not a refusal.

## 6. Update sequences
**Who triggers.** An update is always triggered from outside kbf. A release reaches a host as a package; for a pool of frontends `kbf-updater` rolls the members one at a time (`docs/design/frontend-proxy.md` section 4). There is no update route (`POST /v1/update/frontend` is answered 503) and no `kbf-installer deploy` verb (`docs/design/gamma-deploy.md` is retired). Setting the desired release directly stays a route of the control API, for a caller that wants nodes alone. kbf shows no update button and polls nothing in this version (section 13).

**Node update.** With a desired release set, the frontend rolls the storage and daemon nodes through the drain system, one storage node at a time (P14 builds on the API):
1. Drain, then `UpdateOrder{ACTIVATE, commit, generation}`; `kbf-update` writes the record (section 4) and does nothing else.
2. Installer fetches and verifies (section 5), then writes `pending_confirm`, flips `previous` then `current` (state first), then restarts the node units named in its code table.
3. Linux: window starts at the first start (`boot-check`), 3 start attempts; macOS armed at activation, `expire` triggers.
4. New kbf reports `ACTIVATED_UNCONFIRMED`; the frontend sends `CONFIRM`. A compromised new release can self-confirm; accepted residual (section 10).
5. No confirm by the deadline (monotonic plus wall), start budget spent, or `REVERT`: revert state first, then links, then restart; report `REVERTED`.
Crash at any step: `reconcile` makes links match `state.json` on next start (**built**). Fetch failure leaves `current` untouched and reports `refused`.

**Frontend update**: not the installer's. The root half starts, stops and updates no frontend, and the proxy (shipped in this package) starts, adopts and swaps none: a frontend's binary is `/usr/bin/kbf`, which the package manager replaces, and `kbf-updater` rolls a pool of frontends one at a time (`docs/design/frontend-proxy.md` section 4, `docs/deploy/kbf-updater.md`). What this document keeps:
- **Orders (three, all from `orders/`, subject to section 4 ordering and floors)**: the root half still understands `frontend_update` (a locator, `{order_id, epoch, generation, verb, commit, window_s}`, with no components and no expected facts), `confirm` (naming the staged commit) and `revert` (`crates/kbf-installer/src/helper/cycle/frontend.rs`), but nothing writes them any more: the proxy's update API that did was removed, and a node never writes a `frontend_update` record.
- **No slots.** `slots/<instance>`, `kbf-frontend@%i` and the frontend `pending_confirm` are not used.
- **gc** also keeps any release directory a live process's `/proc/<pid>/exe` resolves into.
- **Operator token.** On frontend and all-in-one hosts `setup` creates `/etc/kbf/api-token` (32 random bytes as hex, 0600, owned by the frontend's user `kbf-server`, also on all-in-one hosts, never overwritten; a Mac runs only `--mode=daemon`, so setup makes no operator token there); `installer.toml` key `operator_token_file` names it, and the proxy reads it for the operator paths. `remote_operator_file` (a CI job's GitHub OIDC token) is still accepted in the `[proxy]` table and nothing reads it.
- `kbf-installer update` and `POST /v1/update/frontend` are removed; the proxy answers the path 503. Node `activate` records never touch the proxy or frontends, on an all-in-one host too.
- `kbf frontend handover`, the `kbf-frontend@.service` template, the Envoy handover and the writer baton are removed.

## 7. Units and gating
Plain files in `packaging/linux/units/`, installed disabled, never enabled by package scripts: `kbf-installer.service` and the proxy's units (the `kbf-installer` package), and one unit per mode `kbf` offers (`frontend` as `kbf-frontend.service`, `storage`, `daemon`, `storage-and-daemon`, `all-in-one`; there is no `node` mode; P11 lists them from `kbf --help`), which the `kbf` package installs. There is no Envoy unit: Envoy's service is its package's (section 5.1). `kbf-signer.service` (frontend and all-in-one hosts only, `User=kbf-signer`, runs the signer release component, local socket for the frontend, gated like the mode units) is installed disabled with the rest. Paths are literal; there are no `@...@` substitutions. The `check-units` rules (`state-store`, `stop`, `credential`, `storage`) move with the units (P11).
```ini
[Unit]
ConditionPathExists=/etc/kbf/kbf.toml
[Service]
ExecStartPre=+/usr/bin/kbf boot-check --mode=<mode>
ExecStartPre=/usr/bin/kbf --mode=<mode> --check
ExecStart=/usr/bin/kbf --mode=<mode>
RestartPreventExitStatus=2
```
(`--config /etc/kbf/kbf.toml` is on the plain frontend unit's `ExecStart` only; kbf reads that file itself.) `kbf boot-check --mode=<mode>` is the schema step of a host from the packages: `kbf` itself, with no other binary to ask, brings the state database named by the `database` key of `/etc/kbf/installer.toml` (`--installer-config` names another file) to the schema it embeds, for the modes that keep state in it (frontend, all-in-one), and counts and reverts nothing, because such a host has no release on trial. A database already past the schema it embeds is left alone, so a `kbf` rolled back to the release before a migration starts on what the later release added; `kbf` itself refuses, when it opens the store, a database with a contract step above what it supports. The check exits 1, and the unit does not start, when it cannot reach the database, a pending migration is not additive or a migration fails. The installer's `boot-check --kbf=<kbf> --mode=<mode>` stays for one release as a wrapper that runs `<kbf> boot-check --mode=<mode> --installer-config=<the host's installer.toml>` and ends as that ended, for the units of the earlier packages; it needs a `kbf` that has the verb.
`--check` is a flag of every mode, prints every missing prerequisite and exits 2 (**to build**, P12; #1020 runs the same checks at every start). It is `ExecStartPre`, not `ExecCondition`, because `ExecCondition` skips silently on exit 1-254. `boot-check` runs as root (`+`) and never counts a start; `kbf boot-check` waits at most 30 s for a lock and at most 10 s to connect, and a schema still busy after that fails the unit (exit 1) instead of holding the start. There is no enrollment pre-start: enrollment runs inside the start of the `storage`, `daemon` and `storage-and-daemon` modes, so a host without a valid token fails its start with one line, and the token decides which of those roles the host may hold.
`kbf-frontend.service` is the only frontend unit (the socket-handover template `kbf-frontend@.service` and `kbf frontend handover` were retired by a maintainer decision). It is for a frontend host without the proxy: `ExecStart=/usr/bin/kbf --mode=frontend --config /etc/kbf/kbf.toml`, with `Type=notify` and the frontend's other keys, and no `--instance`, no `--handover-socket`, no slots and no `RuntimeDirectory`; `kbf boot-check --mode=frontend` stays as its first `ExecStartPre` (it migrates the state database to the schema that `kbf` needs). A host with `kbf-proxy` runs each pool member as a unit of its own; the proxy starts none (`frontend-proxy.md` section 1). Two units of one host bind different listeners (`base=` of each member in `docs/deploy/kbf-updater.md`).

### The metadata log across a rollback

A release may raise the metadata log's machine version the first time it starts (kbf#1278), and an older binary refuses a raised log, so a revert that only moved the links would leave a node that cannot start. `boot-check` therefore handles the log (`meta_log.rs`), on the hosts whose `kbf.toml` names one (`all-in-one`: `[stores] meta-dir`; `storage` and `storage-and-daemon`: `[storage] meta_dir`, default `<[dirs] state, /var/lib/kbf>/meta`):

- **Save.** At the first start of a release on trial (`ExecStartPre`, after the old process stopped and before the new one starts: the only point at which nothing writes the log; `systemctl restart` has no stop of its own to hook) the log is copied to `releases/<older>/meta-log.backup/` (`for`: the release started on it; `log/`: the directory with modes and owners, absent when the node had no log yet), built under `.meta-log.backup.tmp`, synced, renamed, so it is whole or not there. A copy already there for this release is kept (a rerun, or a kill between the copy and the state write); one for another release is put back first. A copy that cannot be made reverts the swap before the release starts and leaves `meta-log.refused` in the state directory; the helper reports it in `status.json` (`refused`, with the reason) and removes it. Only one copy is kept (making one removes the others); `gc` takes it with its release.
- **Restore.** At a start of a release that holds a copy as `current` (the swap away from it was reverted, by `boot-check`, the window, a `revert` order, or rolled back), the log is put back before it starts, if it differs from the copy, and the copy is removed. What the log committed while the newer release ran is not kept.
- **Not covered.** macOS (no start hook), and a start that takes longer than the unit's start timeout because the log is large.

`kbf-installer.service` (no socket unit): `Type=simple`, `Restart=on-failure` with exit 4 treated as success, `ConditionPathExists=/etc/kbf/installer.toml`, `ExecStart=/usr/bin/kbf-installer run` (no `--unit`: `run` restarts the unit of the `mode` in `kbf.toml`, which `setup` enabled, so one unit serves every mode), no `ExecStartPre=` until `check` is built (P10; a stub there fails every start), hardening (`NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/kbf-installer /run/kbf-installer`, `PrivateTmp`, trimmed capabilities); P11 lints the `systemd-analyze security` score.macOS: launchd plists in `packaging/macos/`; nodes only, via cask or `.pkg` (a formula cannot place a root LaunchDaemon, #966). `kbf-installer` there is root-owned; a user-owned prefix is refused by `check`.

## 8. Compatibility and migration
- Wire: the frozen messages stay, plus the one additive change of #1024 section 5, made together with its tests: `UpdateOrder.generation = 6` and `UpdateOffer` `protocol = 5`, `min_protocol = 6`, `state_schema = 7`, `profile = 8` (older peers ignore them; zeros are refused fail closed). `update_order = 9`, `update_status = 7` unchanged.
- Offers stay on the wire and nodes consume them: the node builds the order record's components, attestation and expected facts from the offer it holds for the commit. `ReleaseService.Fetch`'s caller is the installer's fetch child, not `kbf`. The planner's "release complete" check reads the release store, whose per-platform version facts document also fills the offer's expected facts; a node order to an incomplete release is refused by the planner.
- Installer vs release: no manifest range. A release declares `protocol`, `min_protocol`, `state_schema` in `--version --json`; the installer refuses (`installer_too_old`) one above what it supports, and any state schema bump needs an installer that knows it.
- Adoption of an old-layout host (`/usr/local/kbf`, `/var/lib/kbf-deploy`, the Mac kit) is installing the kbf and kbf-proxy packages (package-update design, section 12); the installer has no `migrate` or `uninstall` verb.

## 10. Security rules
Threats: A compromised `kbf`; B compromised fetch child or release host; C local user; D old or malicious signed release. Root is out of scope.
- S1. Authority comes from the channel: only `orders/` carries wire orders (section 4). S2. Wire orders act on a fixed code table of node and daemon units; unit and instance names never come from order content.
- S3. Release monotonicity: (epoch, generation) rule, operator floors, trust-file `deny` list; only `rollback` goes lower. S4. `source_refs` narrows only; no PR or feature-branch refs in the default.
- S5. One pass: hash while reading the pipe; the child can create no file. S6. The probe runs on the file that is renamed, extracted by root. S7. Every artifact is bound to the order commit (`--source-digest`). S8. Names and versions are validated, never free-form. S9. `SHA256SUMS` is advisory; trust is the attestation, and the record's digest is only a locator.
- S10. Spawn hygiene, caps, network rules, dedicated uids, download directory outside the root tree (section 5). S11. The node identity is lent over a descriptor and a compromised child can steal it (accepted v1 residual; follow-up P15).
- S12. `window_s` clamped. S13. One activation at a time, minimum interval, `previous` only confirmed. S14. Strict record parsing: duplicate keys refused, ids and generation bounded, dot names ignored, one read into memory.
- S15. `--root` absent from release builds; environment variables ignored; `gh`, `systemctl`, `launchctl` run by absolute path with an empty environment, `GH_NO_UPDATE_NOTIFIER=1`. S16. Trust files expire; the trust root cannot self-update, so revocation ships as a package. S17. The package signing key is the root of trust; packages are signed before any public channel (decision 7).
- S18. Envoy is outside the attested set: it is a host prerequisite whose version `check` compares to a tested range. It carries traffic, never authority; a bad Envoy can drop or delay builds, not forge an order or a release.
- S19. Stage, fsync, rename, fsync parent, then state. S20. A directory is not proof (section 5 step 7). S21. ## 14. State database schema (frontend and all-in-one hosts)
Postgres is a runtime dependency of these two modes and the installer owns its schema. kbf creates and alters nothing; it only checks the version at its own start.
- **Where.** `database = "postgres:///kbf?host=/run/postgresql&user=kbf-server"` in `installer.toml`. A URL with a password is refused (the file is world-readable); no message quotes the URL. Given no `--database`, `setup` uses `postgres:///kbf?host=/run/postgresql&user=kbf-server` and makes the role and the database on the local server (as the superuser over the socket, peer authentication; `--create-local-database` does the same for a URL you give); a URL given without the flag names a role and database that exist before `setup` runs. Setup prints the `pg_hba.conf` lines the logins need and never edits the file. `docs/deploy/kbf-installer-setup.md`, "The state database".
- **Migrations** are SQL files embedded in the binary (`crates/kbf-state/src/postgres/migrations/NNNN_name.sql`), numbered from 1 without a gap, each applied in its own transaction together with its `schema_version` row, under an advisory lock. The first line says `-- kbf-migration: expand` or `contract`.
- **`setup --mode=frontend|all-in-one`** creates the schema on a fresh database, or brings an older one forward; a dry run without `--apply`. Idempotent.
- **Updates.** Before the helper moves the links for an `activate` order, it applies the embedded migrations up to the `state_schema` the release it just fetched reports (`kbf --version --json`, now the Postgres schema version). A refusal (the installer embeds fewer migrations than the release needs, or the next one is a contract step) stops the swap and is reported in `status.json`. The rule is that the staged commit equals the order's: an order for any other release asks for no migration, the log says `state schema: no migration for order N: ...` and kbf's own start check covers it. The staged release stays staged after its swap, so a repeat of its activation asks again (idempotent, and refused while the database is down). `kbf-installer run --installer-config PATH` turns the step on; `run` refuses to start (exit 2) without it when the unit it restarts is `kbf-frontend@<instance>.service`, `kbf-all-in-one.service` or `kbf-all-in-one@<instance>.service`, because the installer is not told the host's mode and the unit is the one place that names it. A launchd label names no mode and is not checked.
- **No frontend swap.** The proxy starts no child and runs no migration. A frontend's schema is brought forward by `kbf boot-check`, the first `ExecStartPre=` of its unit, with the migrations embedded in the `kbf` it starts (`frontend-proxy.md` section 11). It uses the `database` URL of `installer.toml` as the role it names; a separate migration role is not supported.
- **Expand only.** An `expand` migration is linted on its text: no `DROP`, `RENAME`, `TRUNCATE`, `DELETE`, column type change, `SET NOT NULL`, `SET DEFAULT`, `UPDATE` of rows, `CREATE OR REPLACE`, `ADD CONSTRAINT` (or `ADD PRIMARY KEY`/`UNIQUE`/`CHECK`/`FOREIGN KEY`) on an existing table, `CREATE UNIQUE INDEX` on a table the file did not create, or `NOT NULL` column without a default (each clause of an `ALTER` is judged on its own). Any migration is refused if it uses `EXECUTE` or controls transactions. A `contract` step ships in a release after the one that stopped using what it removes, and no update applies one. Nothing runs a contract step yet; the verb that will is a later unit.
- **kbf's start check.** kbf supports versions `MIN_SUPPORTED..=latest embedded`. A schema above that range is accepted while every row above it is `expand` (so a release reverted after its successor migrated starts again); a `contract` row above it, a version below the minimum, or no schema is refused with one line. Only the first connection of a store is judged.
- **No migration of old state.** A database that holds tables without a `schema_version` table (a store made before schemas were versioned) fails migration 1 with a line saying so; the farm starts fresh.
